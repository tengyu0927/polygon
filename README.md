# 站点日最高气温预报系统

8 个民航机场（ZBAA 北京首都、ZSPD 上海浦东、ZGGG 广州白云、ZGSZ 深圳宝安、
ZUUU 成都双流、ZUCK 重庆江北、ZHHH 武汉天河、ZSQD 青岛胶东）的日最高气温预报。

两条独立路线：

- **D+1/D+2 路线** —— 用 GFS 固定时效预报做 MOS 订正，提前 1-2 天
- **临近路线** —— 用当天上午实况外推当日峰值，提前 1-6 小时

## 零、新机器上怎么跑起来

```bash
git clone <你的仓库地址> && cd ploygon
pip3 install -r requirements.txt      # 可选，缺了也能跑（见下）
./bootstrap.sh                        # 建数据，完整版约 1.5-2 小时
python3 check_consistency.py          # 确认环境没问题，18 项应全过
./run_hourly.sh                       # 出预报
```

**仓库里没有数据**：实况库 510MB + 6 个模式库约 1.2GB，远超 GitHub 单文件
100MB 的硬上限。全部可由 `bootstrap.sh` 重建 —— 代价是时间不是信息。

| 命令 | 建什么 | 耗时 | 能跑什么 |
|---|---|---|---|
| `./bootstrap.sh --obs-only` | 只建实况库 | 30-60 分钟 | 12-15 时的纯实况档 |
| `./bootstrap.sh --quick` | 最近 2 年实况 + 6 模式 | 约 1 小时 | 全部预报，但重训时长序列不足 |
| `./bootstrap.sh` | 1995 年起实况 + 6 模式 | 1.5-2 小时 | 全部，含重训 |

**模型权重是随仓库走的**（`model.json`、`nowcast_nwp.json`、`nowcast.json`、
`nowcast_late.json`，共 7MB），所以数据一建好就能直接预报，不必先训练。
模型会随天气型漂移，建议按第四节的周期重训。

### 依赖

**核心推理不需要任何第三方库** —— 模型 JSON 里只有权重，纯标准库就能算。
`requirements.txt` 里两个都是「有则更好，无则自动降级」：

- `numpy`：训练提速几十倍。缺失时走纯 Python 实现，**结果一致**
- `scikit-learn`：岭回归+GBM 融合里的 GBM 部分。缺失时 `predict_mos.py`
  自动降级为纯岭回归并打警告，**D+1 会从 1.00 退到 1.08**

> `/usr/bin/python3`（通常没有这两个库），融合静默降级且不报错：
> ```cron
> PATH=/opt/homebrew/bin:/usr/bin:/bin
> ```

## 一、目前哪种最准

所有数字为**取整后**的 MAE（℃）。真值是整数度，取整是上线口径，
它让 ±1℃ 命中率白涨约 15 个百分点而 MAE 几乎不变。

| 时效 | 方法 | 脚本 / 模型 | MAE | ±1℃ |
|---|---|---|---|---|
| 48 小时 | 六模式 MOS D+2（DEB + 岭回归+GBM 融合） | `predict_mos.py` / `model.json` | **1.17** | 72% |
| 24 小时 | 六模式 MOS D+1（DEB + 岭回归+GBM 融合） | `predict_mos.py` / `model.json` | **1.00** | 78% |
| ~6 小时（09 时截止） | 临近 + 六模式 | `predict_nowcast.py` / `nowcast_nwp.json` | **0.87** | 80% |
| ~5 小时（10 时截止） | 临近 + 六模式 | `predict_nowcast.py` / `nowcast_nwp.json` | **0.81** | 83% |
| ~4 小时（11 时截止） | 临近 + 六模式 | `predict_nowcast.py` / `nowcast_nwp.json` | **0.71** | 86% |
| ~2 小时（12 时截止） | 临近 + 六模式 | `predict_nowcast.py` / `nowcast_nwp.json` | **0.61** | 91% |
| ~1 小时（13 时截止） | 临近 + 六模式 | `predict_nowcast.py` / `nowcast_nwp.json` | **0.46** | 96% |
| 14 时截止 | 临近 纯实况 | `predict_nowcast.py` / `nowcast_late.json` | **0.39** | 98% |
| 15 时截止 | 临近 纯实况 | `predict_nowcast.py` / `nowcast_late.json` | **0.18** | 98% |

> 临近那 7 行全部来自**同一个滚动回测**（2026-04-25~07-24，每档 728 站日，
> 均值决策 = 生产口径），可以直接横向比较。以前 14/15 时用的是年份切分
> （n≈7496）与其他行不可比、且报的是 ±1窗口决策的 MAE，现已统一。

**参照物**：GFS 原始输出（不做任何订正）D+1 是 1.73；机场 TAF 报文的 TX
在 15.9-27 小时时效上是 1.26-1.53。

### 怎么读这张表

**14/15 时那两行不要当真。** 14 时截止时 71% 的日子最高温已经出现，
15 时是 89% —— 那部分不是预报，是复述已知事实。只看真正需要预报的日子
（未见顶），14 时是 0.70、15 时是 0.85，**反而比 13 时的 0.64 更差**。
因为越晚截止，剩下的越是"峰值异常偏晚"的硬骨头。

**实用甜蜜点是 12-13 时截止。** 再往后整体数字好看，但没有增量信息。

**09 时是个分水岭。** 纯实况在 09 时只有 1.35，输给 24 小时前的 D+1（1.15）——
上午的观测告诉不了你午后云和天气系统怎么演变。加上 NWP 特征后变成 1.02，
反超。到 11 时纯实况已经能到 0.96，NWP 的边际价值降到 +0.14。

### 口径提醒

- 09/11 时那两行与 D+1/D+2 是**同一测试集**（2026-03-07 起，n=1104），可直接比
- 12/13/14/15 时用的是年份切分（测试期 2024-2026 全年，n≈7496），
  季节构成不同，跨行比较要留意
- 整数量化给 MAE 设了约 0.25℃ 的地板，别追一个物理上达不到的数

## 二、脚本清单

### 实测口径核对: 必须与 Weather Underground 一致（2026-08-01）

**最终对错以 WU 页面上的日最高温为准**，而我们训练/检验用的是 IEM ASOS 归档的
METAR。两者若不一致，模型学的是 A 的规律、被 B 打分，会留下改不掉的系统偏差。

用 `wu_check.py` 核对 2026-01-01~07-31（212 天）：

| 站 | 与 WU 完全相同 | 差 ≥2℃ | 平均差 |
|---|---|---|---|
| 北京 / 上海 / 广州 / 武汉 / 重庆 | **100%** | 0% | ±0.00 |
| 成都 / 青岛 | **99%** | 0% | −0.01 |
| **深圳** | **29%** | **25%** | **+0.42** |

**7 个站零差异，口径完全一致，不存在偏差问题。**

#### 深圳的根因: WU 挂错了站

WU 的 `ZGSZ:9:CN` 返回的 `obs_name` 是 **Lau Fau Shan（流浮山）** ——
香港天文台在新界后海湾的站（WMO 45035），**离深圳宝安机场约 30 公里**，
根本不是 ZGSZ 的 METAR。试过 `VHHH:9:HK`、`59493:9:CN`、`CHGD9820:1:CH`，
**WU 没有任何 id 能给出深圳宝安的观测**。

差异**不是常数**（标准差 1.34℃，25% 的日子差 ≥2℃），减固定偏差修不掉。

按两套实况分别给深圳的临近预报打分（2026-06-01~07-30）：

| 起报 | 按我们的实况(ZGSZ METAR) | 按 WU(流浮山) |
|---|---|---|
| 9 时 MAE | 0.850 | 1.283 |
| 13 时 MAE | **0.267** | **1.133** |
| 13 时 ±1℃ | **100%** | **65%** |

**我们对深圳宝安报得几乎完美，但按 WU 打分只有 65%** —— 因为在给另一个站打分。

#### 日常核对

```bash
python3 wu_check.py                              # 最近 60 天全部 8 站
python3 wu_check.py --start 2026-01-01 --end 2026-07-31
python3 wu_check.py --stations ZGSZ --hourly     # 单站逐时明细
```

判据是「完全相同」比例，**不是站名** —— WU 用自己的写法
（Beijing/Capital、Qingdao/Liuting 等），名字不同不代表站不同。

**已加进 `run_daily.sh` 每天自动跑**（核对最近 7 天，对不上就打 `[WARN]`，不中断预报）。

#### 已处理: 深圳改用 WU 的流浮山序列（2026-08-01 上线）

按「以 WU 为准」的原则，`wu_obs.py --migrate` 把 `cn.sqlite` 里 ZGSZ 的观测
换成了 WU 那条序列（原 METAR 259,092 条完整备份在 `obs_zgsz_metar` 表，
`wu_obs.py --restore` 可回滚）。切换后 **8/8 站与 WU 100% 一致**。

**为什么直接换实测，而不是学一个「ZGSZ → 流浮山」的转换**
（624 天、2024-07~2026-07、按时间 7:3 切分，目标=流浮山日最高温）：

| 13 时方案 | MAE | ±1℃ |
|---|---|---|
| ZGSZ **真实** tmax + 常数偏移（转换法的**理论上限**）| 1.030 | 57% |
| 只用 ZGSZ 上午实测 | 1.015 | 55% |
| **只用流浮山自己上午实测** | **0.631** | **89%** |
| 两站上午实测合用 | 0.575 | 89% |

用目标站自己的上午实测，比转换法的天花板还好 0.4 度 —— 与全项目的主线结论一致：
**只有站点自己的温度计知道这个站点**。

**三个代价，必须知道**：

1. WU 不给 `clds` / `wx_phrase` / `vis`，深圳的 `cld_now`、`cld_mean_am`、
   `ts_am`、`ra_am`、`obsc_am` 五个特征全空，靠中位数填补＋缺测指示位参与。
   输出里深圳那行不再有「上午云量」备注。
2. 流浮山 2024-07 前是 8 条/天（三小时一次），临近预报一天都用不了。
   **深圳只有约 2 年可用历史，其余 7 站有 30 年**，所以它走「合并」模型而非分站。
3. **所有读实况的入口都要跟着换**，否则你盯的和打分的不是一回事:

   | 入口 | 处理 |
   |---|---|
   | `predict_nowcast.py --live` | `WU_STATIONS` / `_overwrite_from_wu()` |
   | **`live_tmax.py`**（实时监看窗口） | 同名机制，`rawOb` 会显示 `WU Lau Fau Shan` |
   | `run_hourly.sh` / `run_daily.sh` | `iem_multi` 之后紧跟 `wu_obs.py --update` |
   | **`bootstrap.sh`**（新机器） | 建库后自动 `wu_obs.py --migrate` |
   | `verify.py` / `taf_compare.py` | 读 `cn.sqlite`，已是 WU 口径 |
   | `taf_bias.py` | **不改** —— TAF 本就是为宝安机场发的，拿宝安 METAR 对它才对。但它的 ZGSZ 与主链路不是同一个站，别混着比 |

   `live_tmax.py` 之前一直显示的是宝安 METAR: 实测 624 天里 **70% 的日子
   与 WU 对不上、26% 差 ≥2℃**，等于盯着一个站、被另一个站打分。已修。

**迁移的实际收益**（深圳，2026-06-01~07-30，同一把尺子 = WU 日最高温）：

| 起报 | 迁移前 MAE | 迁移后 MAE | 前 ±1℃ | 后 ±1℃ |
|---|---|---|---|---|
| 9 时 | 1.283 | **0.933** | 62% | **80%** |
| 11 时 | 1.133 | **0.717** | 70% | **88%** |
| **13 时** | 1.133 | **0.533** | 65% | **98%** |
| 全部 | 1.183 | **0.728** | 66% | **89%** |

**回归检验**：同一套回测下其余 7 站 **0/10206 条预报发生变化**，Δ = +0.0000 ——
迁移只碰了深圳，没有波及任何其他站。

4. `predict_nowcast.py --live` 从 AWC 取的是深圳宝安 METAR，**必须覆盖** ——
   已加 `WU_STATIONS` / `_overwrite_from_wu()`，每轮会打印
   `ZGSZ 改用 WU 实况（Lau Fau Shan），当天 N 个小时`。取不到会退回读库并告警，
   绝不静默用 METAR。

**踩过的第二个坑（已加兜底）**：`climatology()` 要求每 (站, 月) ≥20 个可用日。
深圳只剩 2024-07 起的数据，按这个门槛**只有 7 月和 12 月过关** ——
而切换当天正是 8 月，`clim_rise` / `clim_peak` / `hours_to_peak` 三个特征
全走中位数填补，**不报错、不留痕，只有翻模型 json 才看得出来**。
已加 `_month_est()`：本月样本不足时退回 ±1 月窗口。
实测其余 7 站的气候态**逐位不变**（最大差 0.000000），深圳补上 8 月。

**踩过的坑（已加护栏）**：`climatology()` 按 `--split-year`（默认 2024）卡训练年份，
而深圳数据从 2024-07 才开始 —— 默认参数下它在气候态里为空，**整个站被静默丢掉**，
预报表少一行也不报错。所以重训必须带 `--split-year 2025`
（2025 而非 2026: 气候态只用 <2025，安全早于日期切分点 2025-12-15，不泄漏）。
`check_consistency.py` 新增「每个时次含全部 8 站」检查，注入验证过能抓到。


### 六个模式的来源与分辨率（2026-08-01 实测确认）

**我们不直接下 NOAA 的 GRIB**，全部走 Open-Meteo API。Open-Meteo 自己的
数据源标注指向 `https://www.nco.ncep.noaa.gov/pmb/products/gfs/`，
但下载、解码、重网格、按点插值都是它做的，我们只拿 JSON。

各模式的格距是**实测**的（沿纬度扫描请求点，看返回的格点中心在哪跳变），
不是抄文档：

| Open-Meteo 模式名 | 格距 | 约合 | 备注 |
|---|---|---|---|
| **`gfs_global`** | **0.1172°** | **13 km** | = 360/3072，即 GFS **0.11°** 产品，非 0.25° |
| `cma_grapes_global` | 0.125° | 14 km | |
| `icon_global` | 0.125° | 14 km | |
| `gem_global` | 0.15° | 17 km | |
| `ecmwf_ifs025` | 0.25° | 28 km | |
| **`jma_gsm`** | **0.5°** | **56 km** | **最粗，每个方向比 GFS 粗 4 倍** |

- **时间步长：逐小时**（实测库里每个 `(站,日,lead)` 恰好 24 条）。
  Open-Meteo 文档：120 小时内逐小时、之后 3 小时一步；我们只用 D+1/D+2，始终在逐小时段内。
- **起报频次**：每 6 小时一次（00/06/12/18Z），预报长度 16 天。
- 我们用 `previous-runs-api` 的 `_previous_day1/2` 后缀锁定时效，
  这是全套流程里唯一能保证不泄漏的取数方式（见「泄漏防护」）。

**关于海拔**：Open-Meteo 会把格点温度按气温直减率订正到请求点的海拔
（实测：强制 `elevation=0/200/500/1000` 时当日最高温 28.3/27.0/25.1/21.8℃，
正好 −6.5℃/km）。**我们从没传过 `elevation` 参数**，它用自带 DEM 取值。
实测 8 站里 7 站的 DEM 与真实场压高差在 2 m 内（影响 <0.02℃），
只有青岛胶东差 +18 m（+0.12℃）—— 这点固定偏差被 MOS 的分站常数吸收，不用管。

**与「格点→站点」那节的关系**：GFS 的 13 km 其实**比 ERA5 的 28 km 还细**，
但站点误差照样在。所以瓶颈不是「格距不够小」这么简单 ——
是任何格点尺度都代表不了停机坪上那一个温度计。

### D+1/D+2 路线

| 脚本 | 用途 |
|---|---|
| `build_mos_dataset.py` | 拉单个模式的固定时效因子 + 拼训练集 |
| `merge_mos.py` | 把 7 个模式的 csv 横向拼成多模式训练集 |
| `run_daily.sh` | **每天跑一次 D+1/D+2**，建议 23 时，见下 |
| `check_consistency.py` | **一致性回归检查**，改完代码必跑，见附三 |
| `verify.py` | **每天累计「预报 vs 实况」**，找站级系统性偏差 |
| `train_mos.py` | 训练并检验，导出 `model.json` |
| `predict_mos.py` | 用 `model.json` 预报指定日期 |

```bash
# 一次性：探测可用变量 -> 拉数据 -> 拼训练集
python3 build_mos_dataset.py probe
python3 build_mos_dataset.py inspect --obs-db cn.sqlite
python3 build_mos_dataset.py fetch --start 2024-01-01          # 约 2 分钟
python3 build_mos_dataset.py build --obs-db cn.sqlite --daily-table daily --out mos.csv

# 六模式: 每个模式各拉一份（--model / --db 换掉即可），再横向拼
python3 merge_mos.py --base mos.csv --extra mos_ecmwf.csv mos_cma.csv mos_icon.csv mos_jma_.csv mos_gem_.csv --out mos_multi.csv

# 训练（定期重跑，见第四节）
python3 train_mos.py mos_multi.csv --coef --dump model.json --pred pred.csv

# 每天预报（追加模式的顺序必须与 merge_mos.py --extra 一致！）
python3 predict_mos.py --ahead 1 --extra-models ecmwf_ifs025,cma_grapes_global,icon_global,jma_gsm,gem_global
```

**多模式把 MOS 也拉起来了**（同一测试集 n=1104，配对自助法）：

| 时效 | GFS 单模式 | **六模式** | ΔMAE |
|---|---|---|---|
| D+1 | 1.21 | **1.08** | +0.133 [+0.086, +0.180] 显著 |
| D+2 | 1.43 | **1.25** | +0.182 [+0.133, +0.231] 显著 |

收益比临近路线还大 —— 时效越长模式误差占比越高，多成员的价值也越大。

**架构会随特征数翻转。** 单模式下分站更优（验证 1.123 vs 合并 1.157），
多模式下合并更优（0.982 vs 1.038）—— 286 列除以 8 个站，分站样本不够。
`train_mos.py` 现在在**验证集**上比一次并把结论写进 `model.json` 的 `prefer` 字段，
`predict_mos.py` 照此选择，不再无条件用分站。

### 每天跑一次 D+1/D+2（什么时候跑）

```bash
./run_daily.sh          # 今天 + 明天
./run_daily.sh 2        # 今天 + 未来 2 天
```

结果追加到 `pred_mos_YYYY-MM-DD.log`。crontab：

```
0 23 * * * cd ~/projects/ploygon && ./run_daily.sh >> cron.log 2>&1
```

**结论：北京时 23:00 跑，不是 17:00。** 但理由不是 TAF 报文发布时刻 ——
本项目的预报不依赖 TAF（那只是对照基线，由 `taf_bias.py` 单独处理）。
真正的约束有两条，都实测过：

**① `recent_bias` 需要今天的日最高温已经定型。** 它是 D+1 模型里重要性排第二的
特征，定义是「过去 7 天实况 − 模式预报」的均值，其中包含**今天**。
而日最高温的峰值最晚可以出现在 17 时 —— 2026-07-25 成都双流就是 17:00 才见顶
（41℃）。17 点跑，等于把一个还没走完的今天当成已知事实，`recent_bias` 偏低，
预报会系统性偏冷。23 点跑，当天已经彻底定型。

**② IEM 归档有滞后。** 实测 2026-07-25 晚 19:00 抓取时，8 个站里有 5 个只归档了
19 条观测；到次日 00:43 补到 24 条。日最高温本身在 19:00 已经正确，
但越晚跑，`prev_tmax` 和 `recent_bias` 的输入越完整。

模式数据不是约束：实测凌晨 00:43 查明天的 `previous_day1` 已经是独立的一轮
（与 `previous_day2` 最大差 2.1℃，不是回退到同一轮），所以 17 点和 23 点在
模式侧差别不大。**卡点在实况侧。**

`run_daily.sh` 里内置了两个守卫：18 时之前跑会明确警告，各站今日观测少于 20 条
也会点名 —— 宁可提示也不静默出数。


**TAF 对照已内置在 `run_daily.sh` 里。** 每天跑完 MOS 顺手抓一次当日 TAF，
把两者并排记进 `taf_compare.sqlite`：

```
  站点      目标日          时效    MOS   TAF TX     分歧
  ZHHH    2026-07-26  D+2      36       33       +3
  ZUUU    2026-07-26  D+2      36       38       -2
```

攒够样本后（TAF 只存 15 天，历史补不回来，**只能靠每天记**）：

```bash
python3 taf_compare.py --analyze                # 回填实况，看谁准
python3 taf_compare.py --analyze --min-gap 2    # 只看分歧 >=2 度的日子
```

**要回答的问题不是「谁整体更准」** —— 那个已经知道了（六模式 D+1 1.08 vs
TAF 1.26-1.53）。要回答的是**分歧大的日子谁对**：如果 TAF 在分歧日赢或打平，
说明预报员看到了模型没有的信息，那 TAF 就该进模型当特征；如果一直输，
这条对照可以彻底关掉。`--analyze` 会分别给「全部」和「分歧子集」两组配对检验。

口径与 `taf_bias.py` 一致：只取落在午后峰值时段（10-19 时）的 TX、排除压在
有效期边界上的 TX（那是「窗口内最大」不是日最高温预报）、同一 (站,目标日,TX值)
只记首次出现（AMD 里的搬运不重复计数）。


**关键设计**：目标量是残差 `y - temperature_2m_max`，不是温度本身；
预报「今天」用的是 24 小时前起报的那一轮（`previous_day1`），与训练同口径，
**不是最新一轮**——用最新一轮会让模型面对没见过的时效。

**选型结论**：分站岭回归（`train_mos.py` 里已验证显著优于合并版 +0.048，
与梯度提升打平）。不需要 sklearn/lightgbm。

| 起报时 | MAE | ±1℃ | 完全命中 | 起报时已见顶 |

| 9 时 | 0.87 | 80% | 39% | 6% |
| 10 时 | 0.81 | 83% | 41% | 15% |
| 11 时 | 0.71 | 86% | 46% | 23% |
| 12 时 | 0.61 | 91% | 49% | 36% |
| 13 时 | 0.46 | 96% | 58% | 51% |
| 14 时 | 0.39 | 98% | 64% | 65% |
| 15 时 | 0.18 | 98% | 85% | 82% |

14/15 时那两行不要当真（见第一节），那时大部分站最高温已经出现。


**业务指标定为 ±1℃ 命中率**（2026-04-25~07-24，728 站日/档，滚动回测实测）：

| 起报时 | ±1℃ 单 / 四 / **六模式** | MAE 单 / 四 / **六模式** | 起报时已见顶 |
|---|---|---|---|
| 10 时 | 79.8 / 81.5 / **82.7%** | 0.933 / 0.838 / **0.824** | 15% |
| 11 时 | 82.6 / 85.3 / **86.3%** | 0.810 / 0.732 / **0.732** | 23% |
| 12 时 | 90.5 / 90.9 / **90.9%** | 0.648 / 0.607 / 0.618 | 36% |

六模式分站 ±1℃（10/11/12 时）：深圳 93/95/100、上海 91/91/98、青岛 81/92/93、
武汉 86/91/89、广州 74/84/96、重庆 77/78/87、北京 76/84/89、**成都 67/71/82**。

**成员数的边际收益在 4 个之后基本饱和**：单→七显著（10 时 ±1 +2.9pt、11 时 +3.7pt），
但四→七在整体指标上三个时次全部无显著差异。**只有大升幅日例外** ——
实际升幅 ≥4 度的 408 个站日上，四→七 MAE 1.21→1.11，Δ=+0.096 [+0.046, +0.145] 显著。
所以六模式值得留，理由是极端日而不是平均表现。

**「完全命中」99-100% 物理上不可达**，别拿它当目标：真值是整数度，命中要求误差
< 0.5℃；12 时未见顶的日子平均还要涨 2-3℃，决定这几度的午后对流、海风锋、云的演变
在上午的地面观测和 25km GFS 里都没有信号。就算「是否已见顶」判得完美（上界），
10/11/12 时也只到 44%/55%/64%。

**`merge_mos.py` 那个「未解现象」已解决**：七模式时代加重复实况列能让 D+1 从
1.18 降到 1.08，机制查不出来。剔除 UKMO 并加入 DEB 后重测，加/不加/精确复制
三个变体全部持平（1.031 / 1.024 / 1.02，配对区间跨 0）。
**那不是普遍现象，是 UKMO 浅归档的副作用** —— 它在 2025-01 前没有数据，
那些"重复列"在缺测时被填成中位数，等于给了模型一个「2025-01 之前」的时代标记。
UKMO 一剔除，标记没了，效果也没了。默认已改成不加重复列（少 46 列）。

**试过、没赢的两个优化**（配对自助法，同一批站日）：

- **换决策规则**。±1℃ 命中的最优解是让 `P(rise ∈ {k-1,k,k+1})` 最大的 k，
  不是均值取整。实现了序贯分类 `P(rise≥k)` + 单调修正 + 窗口 argmax
  （`--` 三种决策并排输出）。结果 80/82/90 vs 均值 80/83/90，三个时次**全部无显著差异**。
- **组合两条路线**（`--blend-mos`）。每块滚动重训 D+1 MOS（训练期也用 walk-forward
  出样本外值，否则组合权重会高估 MOS），当特征喂给临近模型。结果 10 时
  Δ误差率 -0.019 [-0.039, -0.001]，**显著更差**；11/12 时无显著差异。
  原因大概是 GFS 的信息已经通过 8 个模式列进来了，MOS 那层订正主要是偏差校正，
  在 0-2 小时时效上没有增量，反而多 4 列噪声。

**赢了的优化：多模式集合**（`--nwp-csv2`）。ECMWF IFS 9km + CMA GRAPES 15km +
ICON 11km 接进来，除各自的 2m 温度/云量/辐射外，还给出**成员离散度**
（`ens_spread`、`ens_max_minus_min`）—— 模式吵得越凶剩余升温越不确定，
模型据此把预报往气候态收，这是单个高分辨率模式给不了的信息。
MAE 三个时次全部显著改善，1→2→4→7 个模式单调递增（4 个之后饱和，见上）。
**成都收益最大**（11 时 ±1℃ 59→68→73%）——
说明成都之前的短板不全是分辨率，也有单模式误差实现的运气成分。

**关于均态化**（多模式会不会削平极端高值）：实测**温度水平没有被削平** ——
可靠性斜率 0.986（单模式）vs 0.984（六模式），预报/实际标准差比 0.986 → 0.991，
最热 10% 日子的偏差 -0.34 → -0.21℃。结构上就削不动:
预报 = 已达最高（实测）+ 剩余升温，方差主要在实测那一截。
削平确实存在，但只在**剩余升温**上，且是 MAE 最优回归的固有性质，
**多模式反而缓解了它**：

| 实际剩余升温 | n | 单模式 ME / ±1℃ | 四模式 | 六模式 |
|---|---|---|---|---|
| 0 度 | 430 | +0.67 / 92% | +0.59 / 93% | +0.59 / 94% |
| 4 度 | 105 | -1.10 / 67% | -0.90 / 69% | -0.83 / 70% |
| ≥5 度 | 69 | **-1.88 / 29%** | -1.26 / 54% | **-1.03 / 61%** |

极端升温日往往是模式一致看好的晴热天，多成员互相印证反而敢报高。

**对策不是去修点预报**（那是零和的，会伤整体精度），而是另给高端情景:
序贯分类（`fit_ordinal`/`rise_pmf`/`rise_quantile`，模型 JSON 里的 `ordinal`）
产出完整的整数升幅分布，取 P90 作为「不排除冲到」值，`predict_nowcast.py --p90` 输出。
实测覆盖率 95%（标称 90%，略保守），只比点预报高 1.2-1.9℃。

> **`--p90` 不提升点预报准确率**，它只是多一路输出。用分布去改点预报已验证无效
> （众数决策、±1 窗口决策与均值取整三个时次全部无显著差异）。
> 它的价值是极端升温日不漏报 —— 播报形如「成都 38℃，不排除 40℃」。

**结论：分站两段式 + 均值决策 + 六模式集合 + P90 高端情景，不加 MOS 组合。**

### 站级偏差追踪（`verify.py`）

`run_daily.sh` 里已内置，每天 23:59 自动跑（那时当天实况已定型）。手动查看：

```bash
python3 verify.py --report            # 全部
python3 verify.py --report --days 14  # 最近两周
```

它从 `cron_hourly.log` / `cron_daily.log` 解析出每一条预报，配上 `cn.sqlite`
的实况，按「站 × 档位」累计平均偏差（ME）与 MAE，并给出 2×标准误做粗略显著性判断。

**为什么要单独做这个**：通用判读规则（模式离散、预计再升等）在小样本上表现参差，
而**站级偏差稳定得多**。头两天的数据已经能看出来：

| 站点 | ME | MAE | 判定 |
|---|---|---|---|
| **重庆江北** | **−1.40** | 1.40 | **稳定偏低** |
| 深圳宝安 / 武汉天河 | −0.60 | 0.60 / 0.80 | 稳定偏低 |
| 青岛胶东 | +0.50 | 0.50 | 稳定偏高 |
| 北京 / 上海 / 成都 | −0.30 ~ +0.20 | ≤0.40 | 无稳定偏差 |

重庆 9/10/11 时三档都是 −2.00，与「46% 的日子 16-17 时才见顶、而最晚档是 15 时」
这个结构性解释吻合。

> ⚠️ 两天的数据**不足以下结论**。同一天同一站的 7 个档高度相关，
> 有效样本约等于「天数 × 站数」，两周（约 110 站日）以上再看。
> 届时若某站偏差稳定且区间不含 0，可考虑在输出层加分站常数订正。


### 怎么读预报输出的备注（判读经验，**待验证**）

`--verbose` 时每行后面的备注不是装饰，能读出「这个数字有多可信」。
但下面的规则**目前只有回测证据，真实前瞻样本还不够**，见文末的验证结果。

```
  ZUUU 成都双流   38    39    34    +3.6   分站两段式 | 气候升温 3.8 | 上午云量 0.19 | GFS 33.7 云98% | 模式离散 2.2
                 预报  不排除  已达   预计再升
```

| 字段 | 含义 | 怎么用 |
|---|---|---|
| `预计再升` | 模型判断还能升多少 | 最重要，但**别当定局**（见下方实例）|
| `模式离散` | 六个模式成员的标准差 | 可信度读数，≥2.0 要警惕 |
| `气候升温` | 该站该月该时刻的历史平均剩余升幅 | 与 `预计再升` 相除，看模型偏离常年多远 |
| `上午云量` | 06 时至截止的平均云量（0-1） | 高云量压制升温空间 |
| `GFS xx 云xx%` | 模式原始值与午后云量 | 与最终预报差得远 = 订正量大 |
| `不排除` | 升幅的条件 P90 | 极端日的上限参考 |
| `分站/合并` | 用的哪个模型 | 正常都是「分站」，**出现「合并」说明该站数据异常** |
| `上午有雷暴` | 06 时至截止**累计**出现过雷暴 | 注意是累计，不是「此刻在下」 |

**回测证据**（728 站日 × 2 档，n=1456）：

| 分层 | MAE |
|---|---|
| 模式离散 <1.0 / 1.0-2.0 / ≥2.0 | 0.51 / 0.57 / **0.86** |
| 预计再升÷气候升温 <0.5 / 0.5-1.5 / ≥1.5 | **0.35** / 0.71 / 0.82 |
| 上午云量 <0.3 / ≥0.7 | 0.62 / **0.49** |
| 有雷暴 / 无 | **0.48** / 0.59 |

**建议的判读顺序**：先看 `模式离散`（≥2.0 = 打折，这条真实数据支持得最好）→
再看 `预计再升`（小 = 相对更准，但不等于定局）→ 算 `预计再升÷气候升温`（≫1 = 模型在赌）。

#### 真实前瞻数据的验证（2026-07-26~28，n=144）

**方向部分一致，但幅度缩水，且有一条反了**：

| 规则 | 回测 | 真实前瞻 |
|---|---|---|
| 离散 <1.0 vs 1.0-2.0 | 0.51 vs 0.57 | 0.68 vs 0.73（一致）|
| 再升÷气候 <0.5 vs 接近 | 0.35 vs 0.71 | 0.67 vs 0.82（一致但差距小得多）|
| 云量 <0.3 vs ≥0.7 | 0.62 vs 0.49 | 0.54 vs **1.00（反了）** |

而且**最该验的两档样本最少**：离散≥2.0 只有 7 条、有雷暴 7 条，测不了。

原因是三天 ×7 档 ×8 站看着有 144 条，但同一天同一站的 7 个档高度相关，
**有效样本只有 24 个站日**。攒够两周（约 110 站日）再回来重验，
在此之前这些规则当参考、别当依据。

#### 六个最大误差的实例（真实前瞻）

| 日期 | 档 | 站 | 报 | 实况 | 差 | 当时的信号 |
|---|---|---|---|---|---|---|
| 07-27 | 12时 | 重庆 | 37 | 40 | −3 | 比值 1.13、**离散 2.2** ⚠ |
| 07-26 | 15时 | 重庆 | 39 | 41 | −2 | 比值 0.75、纯实况档无离散 |
| 07-27 | 9时 | **武汉** | 30 | 32 | −2 | **比值 0.03（判定基本见顶）**、离散 1.6 |
| 07-27 | 9时 | 重庆 | 38 | 40 | −2 | 比值 0.86、**离散 2.2** ⚠ |
| 07-27 | 10时 | 重庆 | 38 | 40 | −2 | 比值 0.98、**离散 2.2** ⚠ |
| 07-27 | 11时 | 深圳 | 28 | 30 | −2 | 比值 0.83、离散 0.6 |

**离散度那条经受住了考验** —— 重庆 4 例全是离散 2.2，当时就该打折看。

**但「比值 <0.5 = 基本见顶」被武汉那条打脸**：9 时报比值 0.03（模型说几乎不会再升），
结果差 2 度。9 点就断言不会再升，本身就是冒险判断。
真实数据里「比值 <0.5」共 30 条，**完全命中只有 15 条（50%）**，
远没到能当定局的程度（回测里那个 MAE 0.35 在真实数据上是 0.67）。

#### 比通用规则更实用的：记住每个站自己的脾气

重庆连续三天被报低（−2 / −3 / −2 / −2），离散度稳定在 2.2 ——
**这不是随机误差，是站级系统性问题**（46% 的日子 16-17 时才见顶，而最晚档是 15 时）。
青岛 07-27 各档一律 +1~+2 偏高。

站级偏差比通用信号更稳定、更可操作。`verify.py` 每天自动累计这个（见下节）。


### 转折日: 已量化的能力边界（占 13%，贡献约 30% 误差）

按「当天 13 时后的实际升幅」与「近 7 天同站升幅中位数」的偏离分层：

| 类型 | 占比 | MAE | 平均偏差 |
|---|---|---|---|
| 常态（偏离 <1 度） | 48% | **0.220** | 0.00 |
| 小偏离（1-2 度） | 39% | 0.557 | +0.05 |
| **转折日（≥2 度）** | **13%** | **1.052** | **+0.99** |

转折日只占 13%，MAE 却是常态日的 **4.8 倍**，且**系统性欠报近 1 度** ——
这一类贡献了总误差的约三成。

#### 模型没有盲从近期，是收缩不足；而收缩不足的部分无法定向修正

| 类型 | 近期中位数 | 模型预报 | 实际 |
|---|---|---|---|
| 常态 | 0.61 | 0.61 | 0.63 |
| **转折日** | 0.98 | **1.33** | **1.97** |

转折日上模型报 1.33、比近期中位数高 0.35，**方向是对的**，只是离实际 1.97 还差 0.64。

但预报时能算的只有「模型预报升幅 − 近期中位数」这个差值，它的识别力是这样的：

| 预报升幅 − 近期中位数 | n | 其中是转折日 | 欠报量 |
|---|---|---|---|
| −1 度 | 123 | 13% | **+0.23** |
| +0 度 | 426 | 3% | +0.11 |
| **+1 度** | 150 | **29%** | **−0.01** |

**能识别出来的那部分（+1 度组）模型已经修正到位（欠报 −0.01）；
剩下欠报的，恰恰是它识别不出来的。** 对已识别的再加码只会变成过报。

#### 2026-07-31 的案例: 六个模式集体报低，我们已经比模式准

| 站 | 实况 | 六模式均值 | 我们 13 时 |
|---|---|---|---|
| 广州 | 33 | **29.8** | 31 |
| 上海 | 37 | 33.4 | **37** |
| 重庆 | 38 | 35.9 | **38** |
| 北京 | 36 | 34.2 | 35 |

**8 个站我们全部比模式集合均值准**，模式平均报低 1.9℃。
广州模式均值 29.8 甚至**低于当时已达的 30℃**，我们已经往上修到 31，实际 33。

**不是我们没听模式，是模式当天集体失误，后处理只修正了一部分。**
后处理能纠正系统性偏差，纠正不了当天的模式集体错误。

也验过一个想法：「当模式预报峰值低于当前已达温度时，说明模式失效，应完全忽略它」——
但这类日子占 46%（最常见），且我们在其上 MAE 最低（0.350）、欠报仅 +0.13，
**模型早就学会不迷信模式了**。

| 起报 | 30h | 6h | Δ | P |
|---|---|---|---|---|
| 9 时 | 1.1424 | **1.0309** | **−0.1114** | **100%** |
| 11 时 | 0.8736 | 0.8197 | −0.0540 | 100% |
| 13 时 | 0.5206 | 0.5076 | −0.0130 | 98% |

9 时 18h 档也有 −0.0580（P=100%）。**八个站全部改善，单调无例外。**

#### 二、进了六模式集合，收益大幅缩水

把集合里的 GFS 成员换成更新一轮的本地 GFS（其余五个模式不变）:

| 起报 | 用哪一轮 | 现生产 | 新 | Δ | **P** |
|---|---|---|---|---|---|
| 9 时 | 前一天 12Z（18h，**真实可用**）| 0.9409 | 0.9384 | −0.0024 | **61%** |
| 11 时 | 前一天 12Z（18h，真实可用）| 0.7682 | 0.7622 | −0.0060 | 85% |
| 13 时 | 当天 00Z（6h，真实可用）| 0.4807 | 0.4745 | −0.0062 | 89% |
| 9 时 | 当天 00Z（6h，**取不到**，仅作上限）| 0.9409 | 0.9119 | −0.0290 | 100% |

**三档全部达不到 P≥95%，加权只有 −0.0049。** 分站还乱
（9 时北京 +0.014、青岛 +0.017 反而变差）。

**根因**: 只换了 **1/6 的成员**，而 ECMWF / CMA / ICON / JMA / GEM
五个全都还是 Open-Meteo 的约 30h 时效，集合被它们拖住。
单模式里 18h 能给 −0.058，进集合只剩 −0.0024 —— 稀释了 24 倍。
只有那一个成员的时效跳得足够大（30h→6h）才拉得动集合。

#### 三、结论与判据

**暂不上线。** 判据是 P≥95%，这三档都没到。
数据难得、代码写好、验证做足 —— **都不是放宽标准的理由。**

两条路能救，按价值排序：

**（推荐）把六个模式一起换成更新的轮次。** 上限明显更高 ——
六个成员全部提前，而不是只提前一个，且**零下载成本**。
卡点只在历史训练数据: Open-Meteo 的 `previous_day0` 判定不了是哪一轮
（见「更新一轮的模式，判定中」那节）。`run0_probe.py` 已接进 `run_hourly.sh`
前瞻记录，攒够一两周后跑 `run0_probe.py --analyze`：

> 一致率 >98% → 历史接口给的就是当时可得的那一轮，六个模式可一起提前
> 不一致 → 只能继续用 `previous_day1`

**（次选）回补 18Z GFS（约 154 GB）。** 9-11 时从 18h 提到 12h。
按 18h(−0.0024) 与 6h(−0.0290) 内插，12h 约 −0.015 ——
**可能刚够到显著线，也可能不够**，投入 154GB 换一个「可能」不划算。
等第一条走通后，本地 GFS 可作为**第七个成员**加入，
那时它的 6h 时效才真正发挥作用。

#### 四、已经建好、可直接复用的东西

| 文件 | 作用 | 状态 |
|---|---|---|
| `gfs_extract.py` | 在归档服务器上抽 8 站序列（scan/survey/timing/extract）| 已用，抽出 726 万行 |

`gfs_live.py` 的验证: 实时取数与本地归档抽取（同一天同一轮）8 站的
tmax / 边界层 / 辐射**逐位相同**（平均绝对差 0.000℃），列名零差异。

**踩到并修掉的两个坑**（都属于「静默丢数据」那类）:

   靠 shortName 匹配会悄悄丢掉这两个变量（第一次跑只出 19 列而不是 26 列）。
   改成**按变量分开下、分开解**: 我们从 `.idx` 就知道每段是什么，不该再问 eccodes。
2. `to_mos()` 漏了 `hpbl_peak_h` / `hpbl_half_h` / `hpbl_slope_pm`，

拿 18h 训练的订正量喂 12h 输入就是训练/预测口径不一致。

### 更新一轮的模式: 机制成立，但集合内不显著（2026-08-02）

**单模式层面是十六次尝试里最大的一次改善；但进了六模式集合后不达标，
所以最终没有上线** —— 结论见上一节「接进生产的闸门」。

#### 一、原始模式层面: 时效每近一档就明显更准

用户本地 GFS 归档抽出 726 万行（855 天、8 站、00Z+12Z、f000-f048 逐时）。
按「起报到目标日 14 时（北京）的小时数」分档，**6484 个四档齐全的站日完全配对**：

| 时效 | 轮次 | MAE | ME | ±1℃ |
|---|---|---|---|---|
| **6 h** | 当天 00Z | **1.854** | −1.093 | 34% |
| 18 h | 前一天 12Z | 1.979 | −1.186 | 32% |
| **30 h** | 前一天 00Z（≈现在用的口径）| **2.092** | −1.256 | 30% |
| 42 h | 前两天 12Z | 2.166 | −1.289 | 29% |

**6h vs 30h: −0.238（−11%），P=100%，八个站全部改善**（广州 −0.41、重庆 −0.33 最多）。
单调、无例外。

#### 二、后处理之后还剩多少（这才是关键）

我们的 MOS 已经把模式的 2.09 修到 1.03、修掉一半 ——
**更准的输入未必带来更准的输出**，所以必须在真回测上验证。

`gfs_local_build.py` 把本地归档转成 mos.csv 的列名，
**A/B 就是「同一套代码 + 不同的 csv」**，没有实现差异混进来。
关键是拿 **`mos_L30` vs `mos_L6`** 比 —— 同一时段、同样样本量、**只有时效不同**，
这样时效的效应不会和样本量混在一起（那正是第 12 次实验的教训）。

| 起报 | 30h（基线）| **6h** | Δ | **P(6h 更好)** | ±1℃ |
|---|---|---|---|---|---|
| **11 时** | 0.8736 | **0.8197** | **−0.0540** | **100%** | 81.8→**83.4%** |
| 13 时 | 0.5206 | 0.5076 | −0.0130 | 98% | 94.7→94.8% |
| **全部** | 0.6971 | **0.6636** | **−0.0335** | **100%** | 88.2→**89.1%** |

分站 7/8 改善：武汉 −0.066、成都 −0.054、重庆 −0.043、北京 −0.035。

**原始层面的 −0.238，后处理后剩下 −0.0335**（MOS 吸收掉 86%）。
但这个残余量仍然是**已知最大的一块** —— 对照第 12 次（归档回填、唯一的另一次胜利）
只有 −0.0114。**这次是它的三倍。**

**而且越早的起报时刻收益越大**（11 时 −0.054 vs 13 时 −0.013）——
早时次实测少、更依赖模式，模式更新的收益就更大。
**这正好对准「越早报准越值钱」这个核心诉求。**

#### 三、`hpbl` 对见顶时刻: 否掉

原以为「混合层什么时候塌」能直接指示见顶时刻（Open-Meteo 的
`boundary_layer_height` 历史归档全空，一直拿不到，所以从没测过）。
实测 6536 个站日：

| 特征 | 与实际见顶时刻的相关 |
|---|---|
| `hpbl_peak_h`（边界层峰值时刻）| **0.034 —— 等于零** |
| `hpbl_half_h`（塌到一半的时刻）| −0.028 |
| `hpbl_slope_pm`（午后塌缩速率）| −0.184 |
| **`t2m_peak_h`（模式自己的温度峰值，对照）** | **0.314** |

**模式的边界层峰值时刻，还不如模式自己的温度峰值时刻。**
分站看上海、深圳甚至是负相关。物理上说得通，数据上不成立 —— 第 16 个被否掉的想法。
（`hpbl` 作为一般特征是否有用另说，要单独测。）


### 本地 GFS 归档: 用更新的一轮换时效（2026-08-01 起，测试中）

用户另一台服务器上有 **NCEP GFS 0.25° 地面场的业务归档**
（`~/bedrock/getdata/gfs_0p25_1hr/YYYY/YYYYMMDD/HH/`），
2024-03-30 至今、每天 00Z 和 12Z、f000-f120 逐小时。
`gfs_extract.py` 拷过去跑，只把 8 个站的序列抽成小 CSV 带回来。

#### 为什么值得做

现在训练和预测都用 Open-Meteo 的 `previous_day1`（约 30 小时时效那一轮）。
本地归档的文件名把起报时刻（`t00z`/`t12z`）和时效（`fNNN`）写死了，
**时效可精确控制、无泄漏歧义** —— 而 Open-Meteo 的 `previous_day0` 判定不了
是哪一轮，只能靠 `run0_probe.py` 前瞻记录等两周。

用 `gfs_extract.py timing` 按 **落地滞后 = 文件 mtime − 起报时刻** 实测
（848 次 00Z / 854 次 12Z，2024-03~2026-08）：

| 轮次 | 起报（北京）| 落地中位 | 服务 | 到 14 时的时效 |
|---|---|---|---|---|
| 前一天 12Z | 20:00 | 次日 00:00 | 9:15-11:15 | **18 h** |
| **18Z**（**归档里没有**）| 02:00 | 06:00 | 9:15-11:15 | **12 h** |
| 当天 00Z | 08:00 | **11:53-12:00** | 12:15-15:15 | **6 h** |
| 当天 06Z | 14:00 | 18:00 | — | 时效为负，无用 |

**七个起报时刻有六个能从 30h 提到 6-18h。**

#### 归档实情（`scan` / `survey` / `timing` 实测）

- 1702 轮起报、8.3 万个文件（`--fh-max 48`），`_surf` 子集约 14 MB/个
- 变量：`t2m` `r2` `u10` `v10` `dswrf` `tp` `prmsl` `tsfc` **`hpbl`** 全程 60/60；
  `sp` `tcc` 从 2024-05-01 起（前一个月缺）
- **`hpbl`（边界层高度）是最值钱的** —— 见顶发生在混合层塌缩的午后转换时刻，
  它是这个过程的直接度量，而 Open-Meteo 的 `boundary_layer_height`
  历史归档全空、一直拿不到
- 缺 `d2m`（有 `r2`+`t2m` 可反算）、`cape`/`prate`（已实测无用）、`gust`（权重极低）
- 00Z 给 13:15 用：f000-f018 晚于 13:15 的比例 1.2%-4.0%，在 5% 线内
- **踩过的坑**：每个数据文件旁有同名零字节 `.OK` 标记，正则不锚定行尾会把它们
  当 GRIB 读，文件数翻倍且全部失败

#### 18Z 的事: **先不下**

18Z（北京 02:00 起报、06:00 落地）能让 9-11 时从 18h 再提到 **12h**。
实测 AWS `noaa-gfs-bdp-pds` 的 18Z **至少回溯 850 天**，且有 `.idx` 索引，
按字节范围只下需要的变量约 **11.7 MB/文件**（整文件 500 MB）。
回补全量约 **154 GB**、十几小时。

**但在验证机制之前不下。** 判据：

> 用已有的 00Z/12Z 数据，在滚动回测上测「当天 00Z（6h）接进模型，
> 是否显著打赢 `previous_day1`（30h）」。**赢了才回补 18Z，没赢就不下。**

理由：时效的价值在**模式原始输出**上是明确的
（Open-Meteo 实测 48h 2.146 / 24h 1.994 / 最新轮 1.770），
但我们的 MOS 已经把模式的 1.99 修到 1.03、修掉近一半 ——
**更准的输入未必带来更准的输出**。这正是要先测的。

零成本的并行选项：让业务下载脚本从现在起加上 18Z，三个月后自然就有训练数据，
不与上面的验证冲突。


### 「用预报历史算偏差、再订正回去」这条路走到哪了（2026-08-01）

被问：不靠气象要素，改成拿历史预报（D+1/D+2/TAF/临近逐时）和实况回顾拟合、
算偏差、再应用到后续预报，是不是也是一种办法？

**这条路的核心部分早就在用，而且是全模型最重要的特征。**
`recent_bias`（近 7 天「实况 − 模式」均值）在 D+1 岭回归里
**标准化系数 +0.631，权重排第一**，远超模式原始温度（−0.365）。

#### 已试：多窗口偏差（第 15 次，未采用）

`recent_bias` 只有 7 天一个窗口、一个简单均值。天气型的持续时间不固定 ——
短窗口跟得快但噪声大，长窗口稳但滞后。加了 5 个量：
`recent_bias_3/14/30`、`bias_trend`（近 3 天比近 14 天更偏 = 偏差在扩大）、
`bias_sd_7`（最近几天错得一致不一致 = 这个偏差可不可信）。

### 「气温一高模式就报低」是怎么回事（2026-08-01 分解）

反复被问：为什么气温一高，模式整体报的就偏低？是不是订正通常往下订？
**两个猜想都不成立，真实原因是三件事叠加。**

**猜想一「模式在高温时系统性报低」—— 不成立。**
按**模式报的温度**分档（14181 站日；不能按实况分档，那有循环）：

| 模式报的温度 | n | 实况−模式 |
|---|---|---|
| −8 ~ 11℃ | 1772 | +0.53 |
| 16 ~ 20℃ | 1772 | +0.63 |
| 24 ~ 28℃ | 1772 | +0.60 |
| 30 ~ 33℃ | 1772 | +0.47 |
| **33 ~ 43℃** | 1777 | **−0.03** |

**最高温那一档反而基本无偏。** 报低更多的是中低温档。

**猜想二「我们的订正往下拉」—— 也不成立。**
订正量（最终预报 − 模式原始）按模式报的温度分档：
最冷档 +0.74、中间档 −0.19、**最热档（31-39℃）+0.00**。
全局订正量 **+0.35**，是**往上推**的。
收缩程度也很轻：预报标准差 / 实况标准差 = **0.98**（分站 0.92-1.00）。

#### 真实原因

**一、这一周模式确实集体报低，但幅度是罕见的。**
2026-07-26~31 的 48 站日：

| | 偏差 | \|误差\| |
|---|---|---|
| **模式原始** | **+1.77** | 2.43 |
| **我们的预报** | **+0.35** | 0.94 |

**模式原始报低了 1.77℃，我们修掉了 80%。** 剩下的 0.35 才是我们的问题。
（持续性高温下数值模式偏冷是已知现象 —— 土壤持续干化、感热通量被低估。）

**二、这一周本来就异常热。** 各站实况在同月历史分布里的百分位：
重庆 **91%**、青岛 86%、北京 85%、上海 78%。

**三、你盯的正是高温天，这本身带来选择效应。**
按**实况**分档时，最高那档的「实况−预报」必然为正：

| 实况所在档 | 实况−预报 |
|---|---|
| 27~31℃ | −0.67 |
| 33~34℃ | +0.67 |
| **36~41℃** | **+0.67** |

因为**实况之所以高，一部分正是「无法预报的随机部分」恰好为正**。
任何无偏预报在「事后挑出的高温日」上都会显得报低 —— 这是回归假象，不是缺陷。
反过来在低温日上会显得报高（上表第一档 −0.67）。

**结论**：这周的 −0.41 里，**模式的锅占大头（原始 −1.77）**，
我们修掉了 80%；剩下的一部分还是选择效应。
**长期回测的 ME 是 +0.06，模型没有固定的冷偏差** ——
所以**不要按一周的偏差去订正**（实测留一天验证：订正后 MAE 0.946 → 1.054，更差）。


### 早时次还能不能改进: 更新一轮的模式（2026-08-01，判定中）

现在训练和预测都用 `previous_day1`（约 24 小时时效那一轮）。
**但 9:15 起报时，实际上已经有更新的一轮了。** 实测原始模式 tmax 误差
（2026-06-15~07-25，287 站日）：

| 口径 | MAE | ME | 与实况相关 |
|---|---|---|---|
| `previous_day2`（~48h） | 2.146 | −0.911 | 0.799 |
| **`previous_day1`（~24h，现在用的）** | **1.994** | −0.845 | 0.834 |
| **无后缀 = `previous_day0`（最新一轮）** | **1.770** | −0.710 | **0.873** |

**更新一轮把原始模式误差降了 0.22℃（0.89 倍）**，这比十四次加特征加起来都大。

**且不是分析场**（逐小时误差比值 0.82-0.92，无断崖 ——
若吃了当天分析场，清晨那几小时会准得反常）：

| 北京时 | 00 | 04 | 08 | 12 | 16 | 20 |
|---|---|---|---|---|---|---|
| run0/run1 比值 | 0.89 | 0.91 | 0.92 | 0.92 | 0.85 | 0.85 |

#### 但有一件事历史数据判定不了

`previous_day0` 对某个**历史日期**返回的究竟是哪一轮？
如果是当天 06Z（北京时 14 点）或 12Z（20 点）的轮次，那么 9:15 甚至 13:15
起报时它根本还没出来 —— **拿它训练就是用未来信息，上线后会当场失效**
（训练时以为有、预报时取不到或取到旧的）。这是本项目最忌讳的那类错误。

**唯一严谨的判定办法是前瞻记录**（`run0_probe.py`，已接进 `run_hourly.sh`，
每轮起报时真实调一次接口存下来，不参与预报、失败不影响预报）：

```bash
python3 run0_probe.py --analyze     # 攒一两周后跑
```

判据写在脚本里：把当时**实际取到的** `previous_day0` 与事后用历史接口
拉的同一天比对 ——

- **一致率 >98%** → 历史接口给的就是当时可得的那一轮，**可以**用来训练，
  下一步在 `build_mos_dataset.py` 里加 `previous_day0` 做 A/B 回测
- **不一致** → 历史接口含有当时还没出来的轮次，用它训练就是泄漏，
  只能继续用 `previous_day1`，或改成每轮起报时自己存一份预报当训练集

**在判定清楚之前不要把 `previous_day0` 接进模型。**
这是目前唯一一条「上限明确、且还没被否决」的路。

反复被问：各站见顶时刻不确定，是不是限制预报准确度的最大难题？
如果能量化见顶时刻，准确度会不会大幅提升？

**先做先知实验定上限**：把「当天真实见顶时刻」直接喂进特征表

**所以第一问的答案是「是」——知道见顶时刻能砍掉四分之一以上的误差。**
而且见顶最飘的站受益最大（重庆 −0.215、成都 −0.247）。
（注意这个上限偏高：知道「17 时见顶」本身就泄漏了「温度一直在升」。）

#### 关键: 判据不是 MAE，是相关系数

加噪先知实验（往真实见顶时刻加高斯噪声）给出收益曲线：

| 见顶时刻误差 | 13 时温度 MAE | 相对基线 |
|---|---|---|
| 基线（不用见顶） | 0.4981 | — |
| **完美先知 0h** | **0.3040** | **−39.0%** |
| ±0.5 h | 0.3416 | −31.4% |
| ±1.0 h | 0.3788 | −24.0% |
| ±2.0 h | 0.4382 | −12.0% |

**但 GBM 的 1.93h 接进去是 0%，与这条曲线对不上。** 原因查清了：

- 加噪先知是「**真值** + 噪声」，方差是满的
- GBM 是「**气候态** + 一点信号」，方差是瘪的 ——
  实测预测值标准差 3.09h vs 真实值 4.05h，**只有 76%**，它把预测收缩到了气候态附近

**所以真正的判据是「与真实见顶时刻的相关系数」，不是 MAE。**
当前 GBM 是 **0.713**；要达到 ±1h 加噪先知那档（−24%），需要约 **0.97**。
**0.713 → 0.97 是个巨大的鸿沟，不是调参能补的。**

#### 行业现状（2026-08-01 检索）

- 预测最高温**数值**的研究和开源实现很多（MOS-X、PPNN、ANET 等）
- 预测最高温**出现时刻**的极少 —— 检索结果明确指出这是「相对少被研究的一面」
- 遥感领域的 DTC 日变化曲线模型（四参数/五参数）确实带「最高温时刻」参数，
  但那是**事后拟合**出来的，不是预报出来的，且针对地表温度而非 2m 气温
- 物理上见顶发生在地表浮力通量转负的「午后转换」时刻，
  由净辐射（太阳几何 + 云的到达时间）和平流决定

### 为什么 38 个因子还是报不准: 可预报性上限（2026-08-01 量化）

反复被问的问题：温度算好报的要素，30 年历史数据，38 个气象因子，
为什么 D+1 还能差 1-2 度，临近偶尔差好几度？

**先排除三个不成立的猜想。**

**猜想一「越临近越差」—— 是真的，但只占 12.4%，而且主要是统计幻觉。**
回测 3888 个站日、9/11/13 三档齐全：

| 9 时的误差 | 9 时 | → 13 时 |
|---|---|---|
| 正好报准（0 度，占 25%） | 0.00 | **0.33** |
| 1 度 | 1.00 | 0.45 |
| ≥2 度 | 2.39 | 0.72 |

**9 时碰巧报准的日子，13 时只可能持平或变坏** —— 条件在「早报准了」上做选择，
必然看到回归。总账上 13 时比 9 时平均少错 **0.532 度**，逐站日 13 时更好占 48%、
打平 40%、更差 12.4%（其中差 ≥2 度的只有 0.8%）。

**猜想二「目标本身是干净的」—— 不是。**
METAR 只报**整数摄氏度**（全部 20 万条抽样小数位都是 0），目标自带 ±0.5℃ 取整误差。
且 8 个站里只有上海、北京、广州是半小时一条（日均 48.9 条），
成都、武汉、深圳、重庆、青岛都是逐时（24 条）。用半小时站做对照，
**逐时采样平均漏掉 0.13-0.18℃ 的峰值** —— 那 5 个站记录的「日最高温」
系统性地略低于真实值，且漏多少是随机的。

**猜想三「模式再准一点就行了」—— 天花板比想象的低得多。**

拿 **ERA5 再分析**当「事后真相」：它同化了全球观测，知道当天实际发生了什么，
是任何格点模式的物理上限。同一批测试集站日（n=1064，2026-03-15~07-25）：

| 方法 | MAE | ±1℃ | ±2℃ | RMSE |
|---|---|---|---|---|
| ERA5 再分析（**事后**，知道当天实况） | 1.27 | **48%** | 81% | 1.57 |
| ERA5 + 各站固定偏差订正 | 1.10 | 53% | 87% | 1.38 |
| **我们的 D+1（提前 24 小时）** | **1.22** | **69%** | 89% | 1.66 |
| 我们的临近 9 时 | 1.02 | 75% | 93% | 1.41 |
| 我们的临近 13 时 | **0.49** | **95%** | 99% | 0.79 |

**我们提前 24 小时的预报，±1℃ 命中率（69%）比事后再分析（48%）高 21 个百分点。**

#### 结论: 误差不在「大气」，在「格点→站点」这一步

ERA5 格点约 25 公里，站点温度计在机场停机坪某一个具体位置。
下垫面、地形、海陆、跑道辐射、甚至仪器周围几十米的环境，格点模式一概不知道。
**这部分误差不随模式变好而减少** —— 因为它压根不是大气问题。

这直接解释了三件事：

1. **为什么加物理因子没用**（第 9、10 次尝试）。38 个因子描述的都是**大气状态**，
   而误差在**大气→站点**的映射上。把大气刻画得再细，也修不了站点代表性问题。

2. **为什么临近预报好这么多**（13 时 MAE 0.49 / ±1℃ 95%）。
   **只有站点自己的温度计知道这个站点。** 上午的实测把「格点→站点」那部分
   误差直接测掉了，剩下的才是真正要预报的下午升幅。

3. **为什么广州最差**。它日最高温的天然变率最小（相邻两天平均只差 2.07℃），
   而 ERA5 在它那儿误差最大（1.56℃）—— **信噪比全场最差**：

   | 站 | 标准差 | 相邻两天平均变化 | ERA5 MAE |
   |---|---|---|---|
   | 广州 | 3.66 | **2.07** | **1.56** |
   | 深圳 | 2.56 | **1.19** | 1.13 |
   | 重庆 | 6.75 | 2.83 | 1.48 |
   | 上海 | 6.44 | 2.55 | **1.03** |

**「30 年历史数据能买到什么」也有了答案**：ERA5 原始 1.27 → 加各站固定偏差订正 1.10，
历史只值 0.17℃。剩下的靠模式集合与非线性项，体现在 ±1℃ 从 53% 提到 69%。

**现实的期待值**：D+1 已经在打赢事后再分析。**要再进一步，只能靠更早拿到该站
自己的实测，而不是更多气象因子。** 这也是为什么「早一小时」这么贵 ——
9 时 MAE 1.02、13 时 0.49，差的那 0.53 度买的是四个小时的真实观测。

#### 第九次: 对流/降水因子（2026-07-31 测，未采用）

**动机**：现有 8 个模式变量（温度、云量、短波辐射、风速、露点、湿度、气压、阵风）
里**没有任何降水或对流量**，而午后雷暴压顶正是广州这类站的主要误差来源。
`previous-runs` 端点不支持气压层变量（850hPa 温度拿不到），但支持
`precipitation` / `cape` / `lifted_index` / `weather_code`，且能锁定起报时刻 = 不泄漏。
已拉 2024-01~2026-07 共 106 万条进 `mos_fcst.sqlite`。

**原始信号确实存在**：按模式预报的午后降水量分档，模式残差（实况−模式）单调上升 ——

| 预报午后降水 | n | 残差均值 |
|---|---|---|
| 无雨（1-4 档） | 5912 | +0.19 |
| 有雨（第 5 档 0.08-7.8mm/h） | 1478 | **+0.75** |

即**模式报雨的日子，它把温度压过头了 0.75 度**（不是雷暴压顶导致我们报高，
是模式怕雨报太低）。抬升指数与残差的相关还**分站变号**：
重庆 −0.369、成都 −0.297 vs 北京 **+0.498**、青岛 +0.177。

**但加进模型后变差**（2025-04-01~2026-07-30 滚动回测，按天配对 bootstrap）：

| 目标 | 基线 | 加对流因子 | P(更好) |
|---|---|---|---|
| 临近 9 时 | 1.0177 | 1.0165 | 58% |
| 临近 11 时 | 0.7976 | 0.8030 | 10% |
| **临近 13 时** | **0.4859** | **0.4933** | **1%（显著变差）** |
| D+1/D+2 | 1.3279 | 1.3225 | 79%（不显著）|
| 广州（目标站） | 0.791 | 0.800 | 变差 |
| 大升幅日 ≥4℃ | 1.215 | 1.217 | 无变化 |

**原因是共线**：`lifted_index` 与 `temperature_2m_max` 相关 **−0.85**，
`cape` 与 `dew_point_2m_peakmean` 相关 0.56。信息已被已有因子覆盖，
加进来只增加方差。样本内 R² 从 0.134 涨到 0.169 —— **那正是过拟合的样子**，
所以样本内 R² 不能当采纳依据。

**代码保留在开关后**（`PLOYGON_CONV=1`），数据留在 `mos_fcst.sqlite` 里不用重拉。
`check_consistency.py` 新增两条护栏，防止它静默上线（见下）。


#### 顺带查清的三件事

**一、物理量本来就在模型里。** `FEATS` 的 38 项含云量（`cld_now`/`cld_mean_am`/
`nwp_cloud_peak`）、辐射（`nwp_swrad_peak`/`nwp_swrad_max`）、降水标记
（`ra_am`/`ts_am`）、露点差（`dpd_now`/`nwp_dpd_peak`）、气压变（`pres_tend_3h`）。
不存在「没量化物理关系」的问题。

**二、纯地面观测量的天花板很低。** 30 年夏季 34176 个站日，13 时的
11 个观测量合起来预测「下午还会再升多少」：**测试集 R² = 0.085**，
MAE 0.902 vs 气候基线 0.954 —— **只赢 5%**。
单变量最强的是风速（AUC 0.327，风大则不再升），但它早就在 `FEATS` 里。

还有个陷阱：**8 站混在一起算 AUC = 0.498（等于没用），分站算是 0.40-0.72。**
辛普森悖论 —— 各站基础率差太远（成都 53.8% 会再升，上海只有 4.2%），
混合会把信号抹平。这也是架构选择里「分站」常赢「合并」的原因。

**三、相似案例法：现有模型已经在案例库的水平上。** 以 2026-07-31 广州为例，
13 时状态（30℃、露点差 6.0、湿度 72%、风 1.0m/s、上午已升 5.0℃）在 30 年里
找最像的 40 天：

| | 下午再升 |
|---|---|
| 广州全部 4447 个夏季日 | +0.72 ± 1.34 |
| 状态最像的 40 天 | **+1.17 ± 1.14** |
| **我们 13 时报的** | **+1.3** |
| 实际 | **+3.0** |

**我们报的 +1.3 和案例库均值 +1.17 几乎一样**，而 40 个相似日里最大的也就是 +3.0
（即实况正好落在案例分布的最边缘）。案例库把标准差从 1.34 只收窄到 1.14，
**没有额外信息可给**。这与第 7 次 kNN 输 7:1 的结论一致。

**顺带**：那天 GFS 给广州报的是 **26.0℃、云量 100%**，实况 33 —— 模式错了 7 度。
我们输出 30，已经在大幅上修模式了。

**现实的期待值**：常态日（约 87%）MAE 0.22-0.56，做得相当好；
转折日（13%）MAE 约 1.05，会错 1-3 度。**这 13% 不是判读失误。**

两处都修了：

- 模型龄检查改成：训练集滞后 ≥2 天就打 `[WARN]`（23 时跑滞后 0 天、跨午夜
  跑滞后 1 天都正常）

**教训**：修「数据没更新」这类问题时，要顺着**整条链路**查到最终被训练读的
那个文件为止，不能只修自己当时注意到的那一段。

#### 失误二: 因为单日表现停用分站规则（当天停用，次日撤回）

07-31 当天，分站规则确实是负作用：

|---|---|---|
| 旧模型 + 分站规则（实际用的） | **1.12** | 2/8 |
| 旧模型，全看预报 | 0.62 | 5/8 |

那天重庆 **14 时**就见顶（平时 15 时、46% 在 16-17 时），武汉预报本就正确，
用「不排除」各多报 1 度 —— **规则的前提当天不成立**。我据此停用了规则。

**这个停用是错的**，用 1 天推翻了 5 天。把六天（07-26~07-31，312 条）算总账：

| 方案 | MAE |
|---|---|
| 全看预报 | 0.740 |
| **武汉+重庆看不排除** | **0.593** |

按天配对 bootstrap 95%CI `[-0.250, -0.015]`，`P(规则更好)=98%`，逐日 **4 胜 1 平 1 负**
（07-31 就是那 1 负）。留一天验证里**武汉、重庆 6/6 折都入选**，
北京 4/6、广州 2/6、深圳 2/6 属折间闪烁的噪声 —— 07-28 把广州深圳加进来
（广州不排除 1.71 vs 预报 0.57），当天就从赢变成输。

**规则在早时次价值最大**，这正是「越早越好」最吃紧的地方：

| 起报 | 晚见顶站用不排除 | 用预报 |
|---|---|---|
| 9 时 | 0.500 | **2.250** |
| 11 时 | 0.500 | 1.500 |
| 13 时 | 0.375 | 1.250 |
| 15 时 | 0.900 | 0.900（已收敛）|

**真正的教训不是「规则不该上线」，是「不该按最近一天改规则」。**
两个错误方向对称：4 天样本就上线太急，1 天翻车就下线同样急。
现已把判据写死在 `verify.py` 的 `LATE_PEAK` 注释里：

> 每周五重跑 `python3 verify.py --report`，仅当某站累计 P(不排除更好) **连续两周**
> 落在 90% 以下才移出；新站加入要求 P≥95% **且**留一天验证全折入选。

当前 `LATE_PEAK = {"ZHHH", "ZUCK"}`。该常量只在 `verify.py` 报表层使用，
不进入预测链路。

#### 那天真正的困难: 四个站晚见顶

广州 16 时（平时 14）、武汉 16、北京 15、成都 19 —— 13 时的信息确实不够。
广州 13 时报 30、实际 33，新旧模型都一样，**这 3 度是当前方法的能力边界**。

诊断显示当天早/晚见顶的分界在**露点差**（14.0℃ vs 6.25℃）和**上午降水**
（0 次 vs 4.25 次），而非云量（0.26 vs 0.27，无区分力）。
但用 30 年数据（19374 站日）检验，露点差与晚见顶率几乎无关
（各区间 35-45% 震荡，中位见顶时刻一律 14 时），分站方向还互相矛盾。
**又是单日现象在大样本上不成立。**

也试了**相似案例法（kNN）**：用 13 时的多要素状态在同站历史中找最相似的 30 天，
取其升幅中位数。赢了气候基线，但**输给现有模型 7:1**（重庆 0.875 vs 0.597）——
现有模型有 67 个特征含六模式预报，kNN 只有 5 个观测量，信息量差太远。

### 「预报」与「不排除」怎么合起来用（`verify.py --report` 每天自动重算）

公式：**最终值 = 预报 + w × (不排除 − 预报)**

`verify.py --report` 会每天用累计的前瞻样本重新拟合 w，并**用留一天交叉验证**
给出诚实估计。截至 2026-07-26~29（4 天，n=192）：

| 站点 | 全量拟合 w | 留出各天时的 w | 稳定？ |
|---|---|---|---|
| **重庆** | 0.9 | 0.9 / 0.9 / 0.9 / 0.8 | **稳定** |
| **武汉** | 0.8 | 0.8 / 0.8 / 0.8 / 0.5 | **稳定** |
| 深圳 | 0.6 | 0.6 / 0.0 / 0.6 / 0.5 | 不稳定 |
| 成都 | 0.5 | 0.6 / 0.8 / 0.0 / 0.0 | 不稳定 |
| 北京 / 上海 / 广州 / 青岛 | 0.0 | 全 0.0 | 稳定为 0 |

**目前只推荐两个站**：**重庆、武汉 → 往「不排除」靠；其余六站 → 直接用「预报」。**

#### 留一天验证：真实收益远小于同批数据上的数字

| 留出日 | 基线 MAE | 套公式 | 改善 |
|---|---|---|---|
| 07-26 | 0.458 | 0.667 | **−0.208（变差）** |
| 07-27 | 0.643 | 0.518 | +0.125 |
| 07-28 | 0.589 | 0.643 | **−0.054（变差）** |
| 07-29 | 0.964 | 0.768 | +0.196 |
| **合计** | **0.698** | **0.646** | **+0.052** |

±1℃ 命中 84.9% → **88.5%**，完全命中 48.4% → 46.9%（略降）。

> ⚠️ **4 天里有 2 天变差。** 在同一批数据上拟合又检验会得出「重庆改善 0.958」
> 这种数字，留一天验证只剩 +0.05。**任何在小样本上选出来的参数都必须这样验**，
> 否则就是自欺欺人。

#### 期望值管理：单天波动远大于公式收益

单天只有 8 个站，一个站错 2 度就能让当天 MAE 跳 0.25 —— 而公式的期望收益只有 0.05。
**所以不要用单天结果判断公式好坏，也不要因为某天差就怀疑系统。**

合理预期：**基线 MAE 约 0.7、±1℃ 约 85%；用公式后 ±1℃ 约 88%，但某些天会更差。**

### 关于精度上限：1-2 度的误差不是判断失误

- 真值是整数度，完全命中要求误差 < 0.5℃
- 12 时未见顶的日子平均还要涨 2-3℃，决定这几度的午后对流**在上午的观测里没有信号**
- 就算「是否已见顶」判得完美，12 时完全命中率上限也只有 **64%**（见第一节的上界计算）
- 现在 ±1℃ 达到 85-91%，**已在物理上限附近**

试过四种方法补那剩下的 10-15%（见顶时刻、午后廓线、风向、方差膨胀），**全部失败** ——
因为那部分信息不存在于任何可获取的数据里。

**建议用 ±1℃ 而非完全命中作为衡量标准。** 业务上「预报 34℃ 实际 35℃」
和「实际 34℃」的差别通常无所谓，而追完全命中会把人逼疯。

#### 取整规则（已核查，不是误差来源）

- **实况不需要取整** —— METAR 原文就是整数（实测 200 条无一例外）
- 预报侧用 Python 的 `round()`，是**四舍六入五成双**（`round(30.5)=30`、`round(32.5)=32`），
  不是四舍五入
- 但连续预报值恰好落在 x.5 的概率极低 —— 实测某日 8 个站**一个都没触发**

这个坑存在但几乎不会发生，**不是误差来源**，无需改动。


### 人工判读: 什么时候信「预报」，什么时候信「不排除」

实况到底落在哪里（回测 n=1456，11/13 时合计）：

| | 低于预报 | **正中预报** | 预报~P90 之间 | 超过 P90 |
|---|---|---|---|---|
| 全部 | 21% | **52%** | 21% | 6% |

看总体没什么用，**关键在按见顶时刻分层**：

| 实际见顶 | 低于预报 | 正中预报 | 预报~P90 | 超过 P90 |
|---|---|---|---|---|
| **≤13 时** | 32% | **62%** | 6% | 1% |
| 14-15 时 | 10% | 45% | 35% | 10% |
| **16 时后** | 8% | 36% | **39%** | **17%** |

早见顶日 62% 正中预报、往上超出只有 7%；**晚见顶日只有 36% 正中，
39% 落在预报与 P90 之间、17% 甚至超过 P90**。

预报时当然不知道今天几点见顶，但**知道这个站通常几点见顶**：

| 站 | 中位见顶 | 16-17 时见顶占比 | 判读建议 |
|---|---|---|---|
| 上海 | 12 时 | 1% | **信 `预报`** |
| 青岛 / 深圳 | 13 时 | 7% / 10% | 信 `预报` |
| 北京 / 广州 | 14 时 | 19% / 13% | 信 `预报` |
| 武汉 | 15 时 | 31% | 偏向 `不排除` |
| **重庆** | 15 时 | **46%** | **信 `不排除`** |
| **成都** | 15 时 | **37%** | **信 `不排除`** |

#### 反直觉的一条: 「P90 = 预报」时反而最危险

| P90 − 预报 | 实况超过 P90 的概率 |
|---|---|
| **0 度**（模型很笃定）| **15%** |
| 1 度 | 6% |
| 2 度 | 1% |

P90 等于预报，说明模型判断「基本见顶、没有上升空间」。**这种笃定一旦错就是大错**。
2026-07-29 成都 14 时报 32 / 不排除 32，结果实际 34，双双失守 —— 正是这 15%。

#### 一条经验公式（对晚见顶站，15 时之前）

> 取 `不排除` 的值；若它等于 `预报`，再 +1

2026-07-29 验证：重庆 11 时 预报36/不排除38 → 取 38（实况 39，仍差 1）；
成都 11 时 预报34/不排除34 → 取 35（实况 34，差 +1）；
武汉 11 时 预报32/不排除33 → 取 33（实况 33 ✓）。
比直接看预报（−3 / 0 / −1）好，但重庆仍不够。

2. **比值今天没有区分力** —— 重庆比值 1.48（已比气候多报近 50%）仍差 3 度，
   上海比值 1.89 只差 +1。

   多云（0.65-0.67）的北京、武汉误差 0/−1。

**GFS 那列的正确用法是看订正量，不是看数值**：

| 站 | GFS | 预报 | 订正量 | 误差 |

| 广州 | 26.2 | 31 | **+4.8** | 0 |

订正量大说明 `recent_bias` 等特征给出强信号、模型有把握；
订正量小说明模型基本认同模式，而模式今天恰好错了。

**当天最危险的组合**: 晚见顶站 + 少云 + 低离散 —— 重庆三条全占，错 3 度。

> 这是一天的数据，且那天恰好是「四个晚见顶站集体被低估」的极端日，
> 推翻不了回测 1456 条上的离散度规律，只说明**它有失效的情形**。
> 主规则不变，等 `verify.py` 攒够两周再统一重估。


### 待验假设: 15 时档对晚见顶日压得太狠

**观察**（2026-07-26~28 连续三天真实前瞻，n=24）：15 时档 MAE 0.38，
反而**差于** 14 时档的 0.33。三天全部如此，不像偶然。

逐条查下来，6 个「15 时比 14 时差」的案例**无一例外都是 16 时后见顶的日子**：

| 日期 | 站 | 见顶 | 14 时预计再升 | 15 时预计再升 | 15 时误差 |
|---|---|---|---|---|---|
| 07-26 | 重庆 | 16 时 | +0.9 | **+0.3** | −2 |
| 07-27 | 重庆 | 16 时 | +0.9 | **+0.3** | −1 |
| 07-28 | 重庆 | 16 时 | +1.0 | **+0.4** | −2 |
| 07-27 | 成都 | 18 时 | +0.5 | +0.3 | −1 |
| 07-28 | 武汉 | 17 时 | +0.5 | +0.3 | −1 |

**机制推测**：15 时的时候历史上 **82% 的日子已见顶**（14 时是 65%），
模型学到「15 时基本不用再升」，把再升幅压到 +0.3~+0.4；
而 14 时还留着 +0.9 的余量，**恰好接住了那些 16 时才见顶的日子**。

**与回测不矛盾**：回测里 15 时（0.176）远好于 14 时（0.386），那是全体平均，
晚见顶日占少数拉不动均值。而这三天有 6/24 = 25% 的样本 16 时后见顶
（重庆连着三天都是 16 时），远高于长期比例，把 15 时的弱点放大了。

**待验，先不动**。三天 24 条里重庆一个站就贡献 3 个案例 ——
这很可能只是「重庆站的老问题」被连续三天的晚见顶放大，而非「15 时档的系统问题」。
`verify.py` 每天累计，**两周后**若 15 时档对 16 时后见顶日的偏低仍然稳定，
再考虑下面两条：

1. 对已知晚见顶的站（重庆 46%、成都 37%、武汉 31% 的日子 16-17 时见顶）
   单独调两段式第一段的判定阈值
2. 15 时档改用 P90 而非点预报作为主输出

> 这是同一个结构性弱点的第三次显形（前两次尝试见上面两节，都失败了）。
> 区别在于: 前两次想从**特征**入手，这次的线索指向**决策阈值**。

#### 2026-07-29 追加: 问题不止在 15 时档，而在所有档

那天四个晚见顶站（重庆 16 时、成都 16 时、深圳 16 时、武汉 15 时）**全部被低估**，
而四个早见顶站（上海/北京/广州/青岛 12-13 时）几乎全对。**所有时效都是负偏差**
（D+2 −0.88、D+1 −0.62、9-15 时 −0.38~−0.88）：

| 站 | 实况 | 见顶 | 各档预报 | P90 |
|---|---|---|---|---|
| 重庆 | **39** | 16 时 | 36-37（−2~−3）| 9/10 时兜住，**11 时起全部失守** |
| 成都 | **34** | 16 时 | 34→33→32（**越晚越差**）| 14/15 时失守 |
| 深圳 | 29 | 16 时 | 28（全程 −1）| 全程兜住 |
| 武汉 | 33 | 15 时 | 30→33（收敛正常）| 除 D+2 全兜住 |

重庆那天连 P90 都兜不住，是目前记录到最严重的一次。
**证据升级**: 不是「15 时档的阈值问题」，而是**所有档对晚见顶日的系统性收缩**
（与「≥5 度升幅那档 ME −1.03」是同一现象的两个侧面）。


### 试过没赢的: 硬判定「已见顶」（第五次，到此打住）

**先做了一个有价值的分解**：13 时为什么比 12 时好这么多？

| 截止 | 总 MAE | 已见顶占比 | 已见顶日 MAE | **未见顶日 MAE** | 未见顶平均剩余升幅 |
|---|---|---|---|---|---|
| 11 时 | 0.706 | 23% | 0.685 | **0.713** | 2.51 |
| 12 时 | 0.610 | 36% | 0.500 | **0.672** | 2.01 |
| 13 时 | 0.460 | 50% | 0.300 | **0.623** | 1.62 |
| 14 时 | 0.359 | 67% | 0.187 | **0.705** | 1.34 |

**13 时优势的三分之二是机械的** —— 一半的天已经见顶，预报等于复述事实。
只看未见顶的日子，11→13 时只改善 0.09（完全命中率 47%/45%/45%，**13 时并不更强**）。

所以「把 13 时的特征搬到 12 时」这条路不存在 —— **没有这样的特征**，
13 时好就是因为它离峰值更近。

> 反直觉的一条: **14 时未见顶日的 MAE 反而最差（0.705）**，完全命中只有 37%。
> 越晚截止，剩下没见顶的越是硬骨头。这印证了「15 时档对晚见顶日压得太狠」。

#### 唯一可挖的是「已见顶判定」，实测挖不动

判定准确率只有 75-83%，且**漏判是误判的 2-3 倍**（12 时 113 vs 43）：

| 截止 | 现在 MAE | 完美判定后 | 可挖空间 |
|---|---|---|---|
| 11 时 | 0.706 | 0.548 | 0.158 |
| **12 时** | **0.610** | **0.430** | **0.180** |
| 13 时 | 0.460 | 0.309 | 0.151 |

12 时可挖的 0.180 恰好大于 12→13 时的差距（0.150）——
**若判定完美，12 时就能超过现在的 13 时**，正好是「提前一小时」。

于是试了硬判定（`--hurdle-thresh`）：两段式现在输出 `P(会升) × E[升幅|会升]`，
即使 P=0.3 也会给 0.6 度，**永远不会真正判定见顶**。改成 P 低于阈值直接输出 0。

| 截止 | MAE | ±1℃ | 完全命中 |
|---|---|---|---|
| 11 时 | 0.706 → 0.705 | 86.3% → **85.9%** | 45.6% → **46.3%** |
| 12 时 | 0.610 → 0.600 | 90.5% → **89.6%** | 49.3% → **51.6%** |
| 13 时 | 0.460 → 0.457 | 95.7% → **94.6%** | 58.4% → **59.9%** |

三个配对检验区间全部跨 0。**完全命中涨 1-2pt，但 ±1℃ 跌 0.4-1.1pt** ——
典型的此消彼长，按主指标（±1℃）净效果为负。

#### 为什么那 0.18℃ 挖不动: 上界存在但不可达

分类器本身是好的，P 与实际见顶率单调对应：

| P(会升) | 样本数 | 实际已见顶 |
|---|---|---|
| 0.0-0.2 | 38 | **87%** |
| 0.2-0.4 | 88 | 73% |
| **0.4-0.6** | **174** | **56%** |
| 0.6-0.8 | 197 | 26% |
| 0.8-1.0 | 247 | 8% |

**但 P=0.4-0.6 那档有 174 条（占 23%），实际见顶率 56% —— 模型说「一半一半」
的时候，真的就是一半一半。** 这不是阈值没调好，是那批日子在观测上本就无法区分。
硬判定把它们全判为见顶，赢一半输一半。

### 五次尝试的总结: 到此打住

| # | 手段 | 切入点 | 结果 |
|---|---|---|---|
| 1 | 预报见顶时刻（观测侧） | 特征 | 失败 |
| 2 | 模式午后廓线 | 特征 | 失败，目标人群更差 |
| 3 | 风向 | 特征 | 信号真但太弱 |
| 4 | 方差膨胀 | 决策/校准 | 校准改善，精度下降 |
| 5 | 硬判定已见顶 | 决策阈值 | 完全命中涨、±1℃ 跌 |

**规律非常清楚: 凡是「模型缺乏分辨力」的问题，调决策规则都救不了 ——
无论是加特征、改分布形状、还是设硬阈值。**

剩下的路只有换更高分辨率的模式（中国区目前无 ≤5km 可用接口，见附四探测结果）。
**这条线到此打住，专心攒前瞻样本。**


### 试过没赢的: 方差膨胀（第四次尝试解决晚见顶）

**诊断先行**：预报的「剩余升幅」被系统性收缩，离散比只有 **0.75-0.83**：

| 实际升幅 | 11 时欠报 | 13 时欠报 |
|---|---|---|
| 0 度 | **−0.68**（报高了）| −0.30 |
| 2 度 | +0.10 | +0.68 |
| 3 度 | +0.65 | **+1.19** |
| ≥5 度 | **+1.22** | — |

两头都错 —— 该报 0 的报高、该报 5 的报低，是最小二乘往均值收缩的固有性质。
于是试 `pred' = mu + c×(pred − mu)`（`--inflate c`），**双向调整**，
不像换 P90 那样单向抬高平常日。

| c | 总 MAE | ±1℃ | **晚见顶 MAE** | 重庆 MAE | ≥3度升幅欠报 | 0度升幅高报 |
|---|---|---|---|---|---|---|
| **1.0** | **0.583** | **91.0%** | **0.868** | 0.714 | 0.90 | −0.42 |
| 1.1 | 0.585 | 90.5% | 0.892 | 0.692 | 0.82 | −0.38 |
| 1.2 | 0.591 | 90.6% | 0.882 | 0.692 | 0.73 | −0.35 |
| 1.3 | 0.605 | 90.3% | 0.892 | 0.698 | 0.66 | −0.34 |

**校准改善了，精度反而下降**：欠报从 0.90 压到 0.66，但晚见顶日 MAE 0.868→0.892、
总 MAE 0.583→0.605、±1℃ 91.0%→90.3%。重庆只降 0.02 且 c=1.1 就到顶。

原因是**膨胀无差别**：它按「预报值离均值多远」放大，但预报值大 ≠ 今天会晚见顶。
真大升幅日被推上去（好），**模型误判为大升幅的日子也被推得更高**（坏），两者抵消。

#### 四次尝试的总结: 问题的本质是「可分辨性」

| 手段 | 切入点 | 结果 |
|---|---|---|
| 预报见顶时刻（观测侧） | 特征 | 失败 |
| 模式午后廓线 | 特征 | 失败，目标人群更差 |
| 风向 | 特征 | 信号真但太弱 |
| **方差膨胀** | **决策/校准** | **校准改善，精度下降** |

前三次说明「信息不够」，第四次进一步说明：**即使不加信息、只调分布形状也救不了**。
根源是模型**无法区分**「今天会晚见顶」和「今天只是模式报得高」——
任何对大升幅加码的手段都会连带放大误判。

**剩下只有两条路**：
1. 接受它，用人工判读补（见上面「什么时候信预报 vs 不排除」那节）
2. 换更高分辨率模式（3km 能分辨盆地地形与局地环流）——
   但 Open-Meteo 在中国区没有 ≤5km 的可用接口（见「归档深度陷阱」一节的探测结果）

**结论：暂停在这条线上投入，专心攒前瞻样本。**


### 试过没赢的: 更多站点实况要素（风向、上午趋势）

问题意识是对的：9 时起报时已知该站前 8 小时的**完整**风温湿压，
但特征里只有最后一条瞬时值 + 温度的三个差分，其余要素的演变都没用上。
试了两组：

**B. 风向**（`wdir_sin/cos`、上午平均风向、风向转角，`_wdir_feats()` 保留）

| 截止 | 不加 | 加 | 配对检验 |
|---|---|---|---|
| 11 时 | 0.706 | 0.706 | 0.000 [−0.027, +0.027] |
| 13 时 | 0.460 | 0.464 | −0.004 [−0.019, +0.014] |

**C. 上午要素趋势**（露点/湿度/风速/云量的 3 小时变化率 + 上午平均露点）

| 版本 | 11 时 | 13 时 |
|---|---|---|
| 全量 6 项 | −0.010 | −0.012 |
| 只留露点+云量 | −0.003 | −0.001 |

两组都不显著，且方向偏坏。C 的解释比较清楚：这些趋势的信息**已被
`trend_1h/2h/3h`（温度自身的趋势）和 `cld_mean_am` 覆盖** ——
上午温度怎么走，本来就把水汽和云的影响都体现进去了。

#### 信号真实性 ≠ 可利用性

这三次失败（A 午后廓线、B 风向、C 上午趋势）分成两类，值得区分：

| | 信号真实吗 | 为什么没用 | 将来还有戏吗 |
|---|---|---|---|
| **A 午后廓线** | **假的** —— 25km 模式对盆地午后廓线本身就不准 | 引入噪声，目标人群反而更差 | 除非换高分辨率模式 |
| **B 风向** | **真的** —— 深圳控制云量后离岸风仍多升 0.76℃ | 太弱（预报的是剩余升幅）+ 样本不平衡（离岸风 307 天 vs 向岸 2042）+ 只对个别站 | **有** —— 样本变多时值得重测 |
| **C 上午趋势** | 真的，但**冗余** | 已被温度自身趋势覆盖 | 不大 |

**A 是方向错了，B 是火候不够，C 是重复劳动。**
下次再想加特征，先问这三个问题，比直接跑回测省时间。


### 试过没赢的: 模式的午后温度廓线

现状是把模式给的 24 个小时值压成 `{var}_max` 和 `{var}_peakmean` 两个数，
峰值出现在几点、午后是继续升还是很快回落，全丢了。而晚见顶正是最大弱点
（重庆站级 ME −1.40，46% 的日子 16-17 时才见顶）。

于是加了三列（`daily_features()` 里已算好，csv 里有，只是不进特征表）：
`t2m_peak_h`（模式预报的峰值时刻）、`t2m_slope_pm`（12→16 时升温速率）、
`t2m_late_minus_peak`（傍晚相对午后均值）。

**结果不采用**，而且失败方式很说明问题：

| 截止 | 不加 | 加 | 配对检验 |
|---|---|---|---|
| 11 时 | 0.706 | 0.699 | +0.007 [−0.015, +0.029] 不显著 |
| 13 时 | 0.460 | 0.459 | +0.001 [−0.015, +0.016] 不显著 |

**目标人群反而更差**：16 时后见顶的日子，11 时档 **+0.078**、13 时档 +0.010；
重庆 11 时 MAE 0.813→0.813 纹丝不动。

根因是假设本身不成立 —— 我原以为「模式知道今天几点见顶，只是被聚合掉了」，
但 25km 分辨率下模式对盆地站的午后廓线**本身就不准**，
用一个不准的峰值时刻去预测另一个量，只是把噪声传进来。

> 这与前一次「用上午观测预报见顶时刻」的失败**同源**：
> 不是信息被压缩掉了，是**这个信息在源头就不可靠**。
> 观测侧、模式侧两条路都试过，都不行。晚见顶的问题目前只能靠 P90 兜底。


### 试过没赢的: 预报「今天几点见顶」

先诊断出一个真问题：**误差随实际见顶时刻单调上升**（728 站日 × 2 档）：

| 截止 | ≤13时见顶 | 14-15时 | 16-17时 | ≥18时 |
|---|---|---|---|---|
| 11 时 | 0.56 | 0.79 | 0.96 | 0.60 |
| 13 时 | **0.28** | 0.56 | **0.77** | 1.20 |

而且见顶时刻是**分站属性**（7-8 月，1995 年至今）：

| 站 | 中位见顶 | ≤13时 | 14-15时 | 16-17时 |
|---|---|---|---|---|
| 上海 | 12 时 | 84% | 15% | 1% |
| 青岛 / 深圳 | 13 时 | 67% / 53% | 26% / 37% | 7% / 10% |
| 北京 / 广州 | 14 时 | 29% / 40% | 52% / 46% | 19% / 13% |
| 武汉 | 15 时 | 23% | 45% | 31% |
| **重庆** | 15 时 | 10% | 43% | **46%** |
| **成都** | 15 时 | 16% | 43% | **37%** |

盆地站近一半的日子 16-17 时才见顶，而最晚的档是 15 时 —— 这解释了重庆为什么
连续多天被报低。模型有 `clim_peak_h`，知道「重庆通常晚」，但不知道「今天会不会晚」。

于是做了两段式：先用上午特征回归当天见顶时刻，再把
`pk_pred` / `pk_minus_clim` / `pk_minus_cutoff` 喂给主模型（`--peak-feat`）。

**结果：不采用。** 七档里只有 13 时显著（+0.019 [+0.007, +0.033]），
9/10/11 时方向偏坏，其余不显著。**测 7 档出现 1 档显著，大概率是多重比较**。
决定性证据是目标人群没站住 —— 16 时后见顶的 102 天上，七档变化正负交替
（+0.010 / 0.000 / −0.029 / +0.020 / −0.020 / −0.020 / −0.010），无一致方向。
机制若真成立，这一层该全线改善。

> 这条留作方法论提醒：**先看目标人群，再看总体显著性**。
> 只盯总体 p 值的话，13 时那个 +0.019 足以让人误判为成功。

晚见顶的问题本身是真的，剩下两条路：给盆地站加 16/17 时档（业务价值随时间递减），
或者接受它、靠 P90 高端情景兜住（已在做）。


### 试过没赢的: 交互项

给临近模型加了 5 个物理上有依据的乘性项（`cld_mean_am × hours_to_peak`、
`ens_spread × hours_to_peak`、`nwp_minus_sofar × hours_to_peak`、
`ts_am × clim_rise`、`dpd_now × hours_to_peak`）。
结果 10/11/12 时 ΔMAE +0.005 / +0.004 / −0.004，**区间全部跨 0**。
`train_nowcast.py` 里 `add_interactions()` 保留，加回 `FEATS` 即可重测。


### P90 高端情景改用分位数回归

原来的 P90 取自序贯分类的整数升幅分布（PMF）。**问题不在总覆盖率而在结构**：

| 口径 | 旧 PMF | **分位数回归** |
|---|---|---|
| 总体覆盖（标称 90%） | 94-95% | 93-94% |
| 平均比点预报高 | 1.12-1.74℃ | **0.96-1.31℃** |
| 按预测升幅分桶的平均标定偏离 | 4.2-4.6pt | **3.0-4.1pt** |

新做法是直接回归条件分位（pinball 损失，IRLS 求解），系数格式与岭回归一致，
**模型 JSON 里仍然只有权重，推理不需要任何机器学习库**。
自检：在已知真值的合成数据上，τ=0.9 实测覆盖 89.2%、τ=0.5 覆盖 50.2%。

**一个统计学要点（踩过才明白）**：诊断时先看到「实际大升幅日的覆盖只有 60-83%」，
于是做了按预测升幅分桶的偏移标定去补。结果**正确口径下的标定反而变差**
（平均偏离 90% 从 3.0pt 涨到 4.0pt）。原因是分位数承诺的是
**给定预测**的覆盖，不是**给定实际结果**的覆盖 —— 后者永远达不到 90%，
除非区间无限宽。追错口径就是这个下场。
`calibrate_quantile()` 保留在代码里并注明未启用，供以后复现。


### 借鉴 PolyWeather 的 DEB（已上线）

[PolyWeather](https://github.com/yangyuan-zhen/PolyWeather)（AGPL-3.0）做的是
Polymarket 温度结算市场的多模式融合，与本项目同域。它的核心算法
**DEB（Dynamic Error Balancing）**值得借鉴：

- 按各模式近 7 天误差的**倒数**加权，误差用指数衰减（0.85^天数）
- 各模式的 signed bias 绝对值进分母做惩罚（样本 <5 天不采信）
- 成员**分歧过大时向等权回退**（原实现阈值 3°F ≈ 1.7℃）

**为什么它能补上我们缺的东西**：岭回归学到的是**固定**线性组合，而 DEB 权重是
近期误差的函数、每天都在变。这种随时间自适应的非线性组合，线性模型表示不出来。

DEB 单独当融合器（`merge_mos.py --deb` 里的 `deb_pred`）：

| 方法 | D+1 MAE（全期 n=6027）|
|---|---|
| GFS 原始 | 1.610 |
| 等权集合平均 | 1.413 |
| **DEB 自适应加权** | **1.361** |

比等权平均好 0.05，但离训练后的 1.00 还远 —— 所以**当特征用，不当预报器用**。
加进 MOS 后（同一批 1099 站日，配对检验）：

| 时效 | 无 DEB | **有 DEB** | ΔMAE |
|---|---|---|---|
| D+1 | 1.082 | **1.031** | +0.051 [+0.010, +0.091] 显著 |
| D+2 | 1.212 | **1.169** | +0.043 [+0.001, +0.085] 显著 |

`deb_weights()` 的数学在 `merge_mos.py` 里，**训练端与预测端共用同一个函数**，
避免两处实现漂移（这个项目已经踩过一次这类坑，见 `m{i}_present`）。

**试过没赢的**：把各模式自己的 `recent_bias` 加进**临近**模型（DEB 的另一半思路）。
10/11/12 时 ΔMAE −0.021 / +0.001 / −0.005，全部无显著差异。
事后想明白: 临近路线已有 `max_so_far`（当天实测），对预报的锚定远强于模式的 7 天
偏差 —— `recent_bias` 在 D+1 时效上系数排第二，一旦有了当日实况就失效了。

### 架构选择改成三方比较

之前只比「合并 vs 分站」，融合被挡在门外: D+1 验证集上分站 0.939 微弱胜过合并 0.948
于是选了分站，而融合是 0.888。现在三方一起比，`prefer` ∈ {pooled, per_station, blend}：

```
── 架构选择（验证集 MAE）
  blend       0.888  <- 上线用这个
  per_station 0.939
  pooled      0.948
```


### 成员不是越多越好：归档深度陷阱

加模式前必须看它的归档起点。**归档只覆盖训练期尾部的模式会主动伤害精度** ——
它的系数只能从少数几个月（还是特定季节）估出来，却要用到全年。

| 配置 | D+1 | D+2 | 配对检验（对 6 模式） |
|---|---|---|---|
| 6 模式（GFS/ECMWF/CMA/ICON/JMA/GEM，均 2024-07 起） | **1.08** | **1.20** | — |
| +UKMO（2025-01 起） | 1.08 | 1.25 | D+2 Δ=-0.047 [-0.084, -0.005] **更差** |
| +UKMO+AIFS（2025-07 起） | 1.17 | 1.40 | 明显更差，ME 变成 -0.42/-0.66 的系统性冷偏 |

所以**生产配置是 6 个模式**，UKMO 与 AIFS 的数据留着但不参与训练。
等它们各自攒够一整年、能落进训练期主体时再重测 —— `merge_mos.py --extra` 加回去
即可，一条命令。

临近路线上同样的比较：去掉 UKMO 后 10/11/12 时 MAE 分别 -0.014/-0.026/-0.008，
方向一致但都不显著；既然方向一致又少拉一个模式（快约 40 秒），一并统一到 6 个。

### 12/13 时也该用模式，之前的结论已推翻

原来 12/13 时用纯实况长序列（1995 年起 7.2 万站日），理由是样本量压倒模式信息。
接入多模式后这个结论不成立了（同一批 728 站日，配对检验）：

| 起报时 | 纯实况 | **六模式** | ΔMAE |
|---|---|---|---|
| 12 时 | 0.716 | **0.618** | +0.098 [+0.043, +0.159] 显著 |
| 13 时 | 0.519 | **0.455** | +0.065 [+0.022, +0.109] 显著 |

`nowcast_nwp.json` 现在覆盖 9/10/11/12/13 五档，`run_hourly.sh` 已同步。
14/15 时仍用纯实况（`nowcast_late.json`）—— 那时大部分站已见顶，模式没有增量。


**关键设计**：目标量是「剩余升温」`Tmax - 截止时刻已达最高`，非负且在 0 处
有大量堆积（12 时截止约 1/3 已见顶）。两段式（`--hurdle`）先判「还会不会再升」
再回归升幅，四个截止时刻都显著优于直接回归。预测截断到 ≥0——
`Tmax ≥ 已达最高` 是恒等式，模型不该违反。

**选型结论**：分站两段式。分站在所有截止时刻显著获胜，且收益随截止时刻推迟
而递减（09 时 +0.103 → 13 时 +0.038）——早上信息越少，站点固有的日变化形态
就越重要。

## 五、已知问题

**ZGSZ 深圳宝安是唯一被模型拖累的站。** 它在临近模型的 11/12/13 时截止上
都输给「气候平均升温」这个常数基线（0.72 vs 0.67、0.61 vs 0.52、0.63 vs 0.54）。
原因大概是信号太弱：深圳 12 时截止时平均只剩 1.4℃ 要涨、标准差 0.6℃，
模型引入的估计噪声超过了它挖到的信号。**建议对该站晚截止时刻直接用气候基线，
或只用 GFS 原值**——值得单独验一次。

**`live_tmax.py` 只监看 7 个站，漏了 ZSQD。** 与 `sites.txt` 的问题同源。
而 ZSQD 恰好常常是各方法分歧最大的站，补上才能验证。

**`sites.txt` 格式与 `--stations-file` 解析器不匹配**（见第二节）。

**盆地站仍是最难的，但没原先想的那么无解。** ZUUU 成都在 D+2 上只从 2.36
改进到 2.01，是唯一没压下去的。临近侧接入四模式后成都 12 时 ±1℃ 从 78% 到 86%，
说明「25km 分辨不出成都平原地形」不是全部原因，单模式的误差实现占了一部分。
**Open-Meteo 在中国区没有 ≤5km 的可用接口**（HRRR 仅北美、ICON-D2/AROME 仅欧洲、
KMA LDPS 无数据；JMA MSM 5km 只覆盖上海和青岛，成都在域外），
所以继续挖只能靠更多模式成员、地形/边界层因子。

## 附：一些反复踩到的坑

- **接口文档与实际行为常常对不上。** 这一路碰到：`hours` 参数无效、
  `recent` 参数被删、GraphCast 退役、时间戳带毫秒和 Z、
  Previous Runs 不支持气压层变量。**先用小样本跑通再上全量**。
- **SQLite 对"文件/表不存在"太宽容。** `sqlite3.connect()` 遇到不存在的文件
  会静默创建空库，`CREATE TABLE IF NOT EXISTS` 撞上异构表也不报错，
  错误往往在下游某个看不懂的地方才爆出来。相对路径的默认值会放大这个问题。
- **同一个数值在不同上下文里含义不同。** TAF 里 TX 是"窗口内最大值"，
  只有当窗口完整覆盖午后峰值时它才等于"日最高温预报"；压在有效期
  起始或末端边界上的 TX 是另一回事。
- **绝不随机划分训练/测试集。** 相邻日天气高度相关。
- **在同一批数据上估偏差再减掉，MAE 必然下降，那是自欺欺人。**
  必须留一交叉验证或时间外推。
- **配对检验才能下结论。** 同一天各站误差高度相关，
  独立算 MAE 再比大小会严重高估显著性。

## 附三、改完代码先跑一致性检查

```bash
python3 check_consistency.py                      # 全部（约 2 分钟，要联网）
python3 check_consistency.py --skip-mos --skip-scripts   # 只查特征与契约，秒级
```

**改完任何代码，这个必须通过才算完。** 它抓的是这个项目反复踩的四类坑：

| 组 | 检查项 |
|---|---|
| ① 特征一致 | 同一站日分别走 `make_samples`（训练）与 `predict_nowcast`（预测）的构造路径，**逐列比对 536 个值**；模型 JSON 点名的列预测端必须全部能产出 |
| ② MOS 对齐 | `model.json` 的 `feats` 与 `mos_multi.csv` 的列；`predict_mos.py` 实跑；实际架构与 `prefer` 相符 |
| ③ 脚本契约 | 两个 shell 的 `MODELS` 一致、与模型要求的成员数一致；一律用 `TZ=Asia/Shanghai`；DEB 训练/预测共用同一实现 |
| ④ **入口脚本实跑** | 在 `env -i PATH=/opt/homebrew/bin:/usr/bin:/bin` 的**模拟 cron 环境**里完整跑 `run_hourly.sh` 与 `run_daily.sh`，断言：输出站数正确、无降级标记、单实例锁生效、D+1/D+2 确实走了融合模型（走不了说明 cron 的 python 没 sklearn） |

两个脚本都支持 `PLOYGON_LOG` / `PLOYGON_TAF_DB` 环境变量覆盖输出路径，
所以检查器实跑不会污染真实日志和前瞻样本库。
`run_daily.sh` 那项约 5 分钟（`predict_mos` 要为 6 个模式各拉 30 天窗口），
急的话加 `--skip-daily`。

### 为什么第 ④ 组必须存在

前面几次"验证通过"用的都是 `--no-fetch`，**把最耗时、最容易坏的取数那段整个跳过了**，结果：

- 删冗余代码时补丁匹配到旧文本，`DBS` 数组被删但循环还在 → cron 里 `unbound variable` 直接崩，本地怎么测都是好的
- `iem_multi --update` 是重抓两整年（8 站约 10 万行），放进每小时任务里，IEM 慢起来挂几十分钟；`urlopen` 的 `timeout` 只管单次 socket 读，服务器涓流发数据永远不触发
- 没有单实例锁，卡住的进程每小时叠一个，互相抢 `cn.sqlite` 写锁，越堆越死

**交互式 shell 的 PATH 与环境和 cron 完全不同，必须用 `env -i` 复现。**
检查器已用注入真实 bug 的方式验证过确实能抓到（`✗ 退出码 0，输出 0 个站`）。

> 检查器自己也会有 bug。第一版报了 48 处不一致，查下来是**它**重算了一份气候态，
> 而生产用的是模型 JSON 里 dump 出来的那份。比对必须用部署的那份参数。

### 日常运维要点

- **实况增量用 `--recent-days N`，不要用 `--update`**。前者 4 秒，后者重抓两整年
- 两个入口脚本都有 `mkdir` 实现的单实例锁（macOS 没有 `flock`），带 PID 存活检测
- 实况更新失败不阻断预报，会打 `[warn]`；模式特征缺失会在**每个站的备注里**打 `⚠`
- 攒前瞻样本期间**冻结代码**。要优化就在副本上做，验证通过后择期一次性上线 ——
  边跑边改的话，日志里混的是不同代码不同模型的输出，没有分析价值
- `run_daily.sh` 单次约 5 分钟，23:59 起跑约 00:04 结束。跨午夜不影响正确性 ——
  目标日在 bash 里就取好并用 `--date` 钉死，与起跑时刻无关

### 已知的、可接受的差异

`backtest_nowcast.py` 与 `train_nowcast.py` 选 alpha 的验证窗口不同
（回测用训练期末尾 90 天，生产用日期分位 0.70~0.85）。两者都合理，
但意味着回测数字与生产模型不会逐条相等。回测是更保守的估计口径，保持现状。

## 附四、将来要加其他机场站点时，时区改造清单

（比如峰值窗口取了错的时段），这类错误不报警、只体现为精度慢慢变差。

build_mos_dataset.py:100 / 140 / 160    "timezone": "Asia/Shanghai"
predict_mos.py:51                       "timezone": "Asia/Shanghai"

改成按站传各自的 IANA 时区名。**注意夏令时** —— 巴黎、伦敦、亚特兰大都有，

这是**本地时**的 10-19 时。跨时区时语义不变（仍是本地 10-19 时），

### D. 数据库 schema

```
build_mos_dataset.py:56  PRIMARY KEY (station, valid_cst, var, lead)
```

`valid_cst` 这个字段名写死了"CST"。存的是本地时字符串，
多时区下含义变成"各站自己的本地时"，**字段名会误导人**，建议改名 `valid_local`。

`cn.sqlite` 的 `obs.local_date` 已经是按 `stations.tz_offset_h` 分站算的，
**这部分不用改**（见下）。

### E. shell 脚本（9 处）

```

```

更麻烦的是 **cron 调度本身**：现在 `15 9-15 * * *` 是北京时 9-15 点。
巴黎的 13 时 = 北京时 20 时，**必须按站分组排不同的 cron 行**，
或者改成每小时跑一次、脚本内部判断哪些站到点了。

### F. 隐含北京时的档位约定

```
run_hourly.sh:49   "只支持 9-15 时"
run_hourly.sh:55   if (( HOUR <= 13 ))    # 9-13 用六模式，14/15 用纯实况
bootstrap.sh:86    --cutoffs 9 10 11 12 13
```

「9-15 时」这个范围是针对中国站的日变化选的。其他站要各自确定
（比如高纬度的伦敦夏季日落晚，峰值时段可能整体后移）。

### 好消息：最难的一块已经做好了

`iem_multi.py` **已经支持分站时区** —— `stations` 表有 `tz_offset_h` 字段，
日聚合 SQL 按站取该字段算日界：

```sql
date(datetime(o.valid_time_gmt + CAST(COALESCE(s.tz_offset_h,8)*3600 AS INTEGER) ...))
```

IEM 的 `--network` 换成 `RC__ASOS`（台湾）、`JP__ASOS`（日本）等即可拉数据，
Open-Meteo 的六个模式对欧美日韩的覆盖只会比中国区更好。

### 关键风险：MOS 会互相影响，临近不会（已实测）

用 4 站训练 vs 8 站训练，对比那 4 站的预报：

| 路线 | 影响 |
|---|---|
| **MOS（D+1/D+2）** | **16% 的预报发生变化，幅度中位数 1 度** |
| 临近（9-15 时） | **完全不受影响** |

原因：MOS 当前用 `blend`（合并模型 + 站点哑变量），所有站共享一套权重；
而临近是**分站独立训练**的（`trs = [r for r in tr if r["stn"] == stn]`），
每个站只用自己的数据。

**所以加站前必须先决定 MOS 怎么办**：

1. 强制 `prefer=per_station` —— 分站独立，但 D+1 从 1.00 退到约 1.14
2. **中国 8 站与新站分成两套独立模型文件** —— 现有精度零损失，代价是维护两套配置
3. 接受相互影响 —— 不推荐，等于拿现有精度换新站

### 判读规则完全不能移植

「13 时最准」「重庆武汉看不排除」这些是**北京时 + 东亚气候型**下统计出来的：

- 13 时对巴黎、亚特兰大毫无意义
- 「看不排除」的规则源于那两站晚见顶（46%/31% 的日子 16-17 时见顶），
  新站要各自统计见顶时刻分布
- 每个新站都要攒**两周以上**前瞻样本才能定规则

### 建议的推进顺序

1. **先把现有 8 站的规则验完**（`verify.py` 攒够两周）
2. 再加 **1-2 个东亚站试水**（东京羽田 RJTT / 首尔仁川 RKSI）——
   时区只差 1 小时、气候型接近，改造成本最低、最容易验证时区改造是否正确
3. 跑通并稳定后，再考虑欧美站（要处理夏令时、cron 分组这些额外复杂度）

**复杂度会实质性增长**：判读规则从 1 套变 N 套、cron 要按站分组、
`verify.py` 报表要分区域、一致性检查要覆盖多时区。
加站前先想清楚多几个站对实际用途的价值是否配得上这些成本。
